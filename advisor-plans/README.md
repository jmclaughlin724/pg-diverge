## Findings considered and rejected (do not re-audit)

- **PERF-06 (deparse fidelity re-parse)**: the "extra parse" of the migration SQL inside `deparseFidelityDiagnostics` is a parse-**cache hit** (the SQL was already parsed at `check.ts:76`), so it saves a `sha256`+`Map.get`, not a libpg-query call. The N per-statement reparses are inherent to the round-trip proof. Negligible — not worth a plan.
- **CORRECT-04 (pre-drop ordering relies on rank, not an explicit edge)**: confirmed there is no active bug; `operationRank` places all drops in a strictly lower band than creates, so the ordering invariant holds today. Architectural hardening only; deferred.
- **CORRECT-05 (`ONLY` spelling for RLS flags)**: rejected against PostgreSQL docs — `ENABLE/DISABLE/FORCE ROW LEVEL SECURITY` never recurses to partitions, so `ONLY` is semantically inert. The existing code comment is correct.
- **CORRECT-07 (lineage marker beyond the 4096-byte read)**: the marker sits ~300–400 bytes into the header; the operations summary cannot plausibly push it past 4096 bytes. Theoretical, no triggering condition.
- **CORRECT-08 (canonical column-ref alias collision)**: could not confirm a real bug; the claimed mechanism contradicts PostgreSQL name resolution and the stripping is scope-correct. Left as an investigate-only note.
- **PERF-08 / "replace `stableJson` with plain `JSON.stringify` in `nodeEquals`"**: two independent verifications disagreed on whether libpg_query guarantees stable JSON key order. Until that is settled upstream, replacing the key-sort is a correctness risk for a small gain. Hold.
- **Security**: no high-value finding. `src/diagnostics.ts` redacts URL credentials, `key=value` secrets, `sb_secret_*`, and JWTs; the CLI top-level `.catch` and JSON output both route through `redactSecrets`; `src/db-admin.ts` uses `try/finally` + `client.end().catch()` with rollback-on-error (no leaks); `src/validators.ts` uses `execFile` with an argv array (no shell injection); `src/sync.ts` `spawn` args are static literals. `npm audit` (prod) reports 0 vulnerabilities. (One dev-only moderate advisory — `js-yaml` via `@changesets/cli`, GHSA-h67p-54hq-rp68 — affects release tooling only; no clean non-breaking bump today. Track, do not block.)

## Direction options (maintainer's call, not ranked against the bugs)

Grounded in repo evidence; each is a design/spike, not a build-everything plan. No plan files written — surface for a decision first.

- **Provider-preset extensibility** — `src/config-contract.ts:98-222` hardcodes 6 provider presets as a closed `readonly` array; new PostgreSQL-compatible platforms require a source edit + PR. A documented contrib path or a lazy `.supaschema/providers/*.json` registry would lower adoption friction. (M, LOW risk.)
- **Batch/programmatic multi-config API** — `src/index.ts` exports per-operation functions but no `batchDiff(configs[])`; orgs with many schema trees loop the CLI per project. A thin orchestration export would unlock monorepo/consistency workflows. (M.)
- **Public-API minimization (elegance decision)** — `src/index.ts` exports ~30 symbols; the README "Library" contract documents ~12. The `db-admin` temp-database cluster (`applySql`, `createTemporaryDatabases`, …) and several typegen/audit/lineage internals have only internal consumers (Code Atlas: `verify.ts`, `corpus.ts`, `benchmark.ts`). Decide which are public; demote or document the rest. Breaking change — best done before 1.0. (M.)
- **Validation-rule plugin seam** — `src/validators.ts` only shells out to external tools; there is no in-process rule hook (`(plan: MigrationPlan) => Diagnostic[]`). A small typed rule interface would let teams enforce org schema policies during `diff`. (M, additive.)
