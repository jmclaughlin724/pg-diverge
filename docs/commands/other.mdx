Use these commands when you need inspection, diagnostics, or shell integration.

Core migration work still starts with `diff`, `check`, `verify`, `types`, `migrations`, and `sync`.

All utility commands accept `--config <path>`.

| Need                                            | Command       |
| ----------------------------------------------- | ------------- |
| See the planned operations before rendering SQL | `plan`        |
| See the extracted schema model                  | `inspect`     |
| Compare schema equality quickly                 | `fingerprint` |
| Check supported and unsupported objects         | `audit`       |
| Run the real-world regression oracle            | `corpus`      |
| Diagnose local setup                            | `doctor`      |
| Validate config paths and sources               | `config validate` |
| Scaffold or repair setup                        | `init`        |
| Add shell completions                           | `completion`  |
| Decode a `SUPA_*` code                          | `explain`     |
| Compare live-catalog normalization              | `selfcheck`   |

<Accordion title="plan — Print the diff plan as JSON">
  `plan` runs the same comparison as `diff`, but prints JSON instead of writing SQL.

Use it to inspect object-level operations before generating a migration.

```bash
# Print the plan from the configured source defaults
npx supaschema plan

# Pipe the output to jq to inspect only table changes
npx supaschema plan \
  | jq '[.operations[] | select(.ref.kind == "table")]'
```

The JSON output is a `MigrationPlan` with an `operations` array. Each operation includes the change type, object key, diagnostics, and destructive/blocking status.

Use `diff` when you need rendered SQL.

Flags: `--from <source>`, `--to <target>`, `--schema <names>`, `--timing`. `--from` and `--to` default to `config.sources`.

  <Tip>
    Use `plan` in a pull-request automation script to post a human-readable diff summary as a comment, so reviewers see the schema impact without running any commands locally.
  </Tip>
</Accordion>

<Accordion title="inspect — Print the schema model as JSON">
  `inspect` prints the schema model supaschema extracted from a source.

Use it when a diff result is surprising and you need to see what supaschema actually read.

```bash
# Inspect a schema directory
npx supaschema inspect --from dir:database/schemas

# Inspect a live database
npx supaschema inspect --from "database:$DATABASE_URL"

# Inspect the schema as it was at a specific Git commit
npx supaschema inspect --from git:HEAD~1

# Filter to specific schemas
npx supaschema inspect --from dir:database/schemas --schema public,auth
```

The output includes supported tables, views, enums, functions, triggers, indexes, and constraints.

Unsupported input appears in `diagnostics` as `SUPA_EXTRACT_UNSUPPORTED` and exits with code `2`.

Flags: `--from <source>` (defaults to the config schema tree), `--schema <names>` (comma-separated filter).

</Accordion>

<Accordion title="fingerprint — Print the model equality hash">
  `fingerprint` prints the canonical hash of a schema source.

Matching fingerprints mean matching schema models, ignoring formatting and comments.

```bash
# Fingerprint a schema directory
npx supaschema fingerprint --from dir:database/schemas

# Fingerprint a live database
npx supaschema fingerprint --from "database:$DATABASE_URL"

# Detect drift: compare directory fingerprint against the database
[ "$(npx supaschema fingerprint --from dir:database/schemas)" = \
  "$(npx supaschema fingerprint --from "database:$DATABASE_URL")" ] \
  && echo "in sync" || echo "drift detected"
```

Flags: `--from <source>` (required).

  <Tip>
    Store the fingerprint of your schema directory in CI and compare it against the live database fingerprint as a post-deploy verification step. A mismatch means the database doesn't match what was declared — a signal that an unapplied migration exists or that an out-of-band change was made directly on the database.
  </Tip>
</Accordion>

<Accordion title="audit — Report schema coverage">
  `audit` reports which objects supaschema can manage.

Use it before adopting an existing database so unsupported DDL is visible before the first generated migration.

```bash
# Audit your schema directory
npx supaschema audit --from dir:database/schemas

# Audit a live database to see how much of it supaschema can represent
npx supaschema audit --from "database:$DATABASE_URL"

# Output as JSON
npx supaschema audit --from dir:database/schemas --json
```

Output is grouped by object type, with supported and unsupported counts.

Unsupported DDL fails closed: `diff` reports `SUPA_EXTRACT_UNSUPPORTED` and stops instead of copying unmodeled SQL into a migration.

Flags: `--from <source>` (required), `--json`.

</Accordion>

<Accordion title="corpus — Run the corpus oracle">
  `corpus` runs the dirty-real regression oracle.

It replays migration files, diffs them against declared schemas, applies the reconciliation migration twice, and requires the next diff to converge to zero operations.

```bash
# Run against the default corpus directory
npx supaschema corpus \
  --database-url postgresql://postgres:postgres@localhost:54322/postgres

# Point at a custom corpus directory
npx supaschema corpus \
  --corpus-dir path/to/corpus \
  --database-url postgresql://postgres:postgres@localhost:54322/postgres

# Output as JSON
npx supaschema corpus \
  --database-url postgresql://postgres:postgres@localhost:54322/postgres \
  --json
```

The command skips gracefully (exits 0 with a notice) when no database URL resolves, so it is safe to include in CI pipelines where the database is optional.

Flags: `--corpus-dir <dir>` (default: `corpus/supabase-style`), `--database-url <url>`, `--json`.

  <Note>
    `corpus` creates and drops databases on the target server. The role must have `CREATEDB` privileges, and the target should be a local or intentionally disposable instance.
  </Note>
</Accordion>

<Accordion title="doctor — Diagnose your environment">
  `doctor` checks local setup and prints pass/fail results.

Run it when setup behaves unexpectedly or before adding supaschema to CI.

```bash
# Check everything except database connectivity
npx supaschema doctor

# Include database connectivity and capability checks
npx supaschema doctor --database-url postgresql://postgres:postgres@localhost:54322/postgres

# Output as JSON
npx supaschema doctor --json
```

`doctor` checks the following, in order:

| Check | What it verifies |
| --- | --- |
| Node version | Your Node.js version meets the minimum requirement |
| Parser | The SQL parser module loaded correctly |
| Config file | `supaschema.config.json` is present, valid JSON, and passes schema validation |
| Database URL | A URL is resolvable from flags, environment variables, or config |
| Reachability | The database accepts TCP connections |
| Auth | The supplied credentials authenticate successfully |
| `CREATEDB` | The connecting role has `CREATEDB` (required for some operations) |
| Migrations history | The history table exists and is queryable |
| Declarative tree | The `schemaPaths` directories exist and contain parseable SQL files |

Each failed check prints a plain-English explanation and a suggested remediation.

</Accordion>

<Accordion title="config validate — Validate configuration">
  `config validate` checks the loaded `supaschema.config.json` for path, source, and credential-reference issues.

Use it before a first migration, after editing path fields, or in an agent workflow that needs structured diagnostics.

```bash
# Print human-readable diagnostics
npx supaschema config validate

# Print JSON for agents or CI
npx supaschema config validate --json
```

The JSON output contains `{ "ok": boolean, "diagnostics": [...] }`. Diagnostics use `error` for invalid config relationships and `warning` for missing directories, absolute paths, source/default mismatches, or inline database URLs that should move to `$ENV_NAME`.

</Accordion>

<Accordion title="init — Scaffold the full setup">
  `init` scaffolds the full supaschema setup in the current directory — the config file, the schema and migration directories, the Claude/Codex agent rules, skills, and hooks, and the `AGENTS.md` / `CLAUDE.md` guidance block. It performs the same setup as package install, for the [contents listed in the introduction](/introduction#what-gets-installed). Like install, it detects the provider layout from the current directory (Supabase, Neon, RDS/Aurora, Cloud SQL, AlloyDB, Azure PostgreSQL, or the neutral PostgreSQL layout).

Run it when npm did not run install scripts — npm v12 ignores dependency install scripts by default — or to repair a setup.

```bash
# Scaffold supaschema setup in the current directory
npx supaschema init
```

`init` is idempotent: existing JSON config files are left untouched unless `--repair` is passed, the agent bundle is refreshed, the managed `AGENTS.md` / `CLAUDE.md` block is updated in place, and hook wiring is merged without duplication. The generated config uses the full shape documented in [Configuration](/configuration/config-file#generated-config).

```bash
# Inspect the scaffold and repair plan without writing files
npx supaschema init --dry-run --json

# Rewrite supaschema.config.json from the canonical contract
npx supaschema init --repair
```

Edit the file when you need named environments, custom schema paths, different output paths, managed schema changes, transaction behavior, or validators.

</Accordion>

<Accordion title="completion — Print shell completion script">
  `completion` prints a shell completion script.

Add it to your shell startup file to autocomplete commands, flags, and source specifiers.

```bash
# Bash
npx supaschema completion bash >> ~/.bashrc

# Zsh
npx supaschema completion zsh >> ~/.zshrc

# Fish
npx supaschema completion fish > ~/.config/fish/completions/supaschema.fish
```

After adding the script, reload your shell (`source ~/.bashrc`, `exec zsh`, or open a new terminal) for completions to take effect. Supported shells: `bash`, `zsh`, `fish`.

  <Note>
    If you install supaschema globally (`npm install -g supaschema`) rather than via `npx`, replace `npx supaschema completion` with `supaschema completion` in the commands above.
  </Note>
</Accordion>

<Accordion title="explain — Look up a diagnostic code">
  `explain` decodes a `SUPA_*` diagnostic code offline.

Use it when CI or a hook prints a code and you need the recovery path immediately.

```bash
# Explain a specific diagnostic code
npx supaschema explain SUPA_CHECK_CASCADE

# Explain another code
npx supaschema explain SUPA_VERIFY_FINGERPRINT_MISMATCH
```

Each explanation includes:

- A plain-English description of the condition
- The command(s) that can emit the code
- Common causes
- Recommended remediation steps
- Links to relevant sections of this documentation (printed as URLs for offline use)

  <Tip>
    If you see a `SUPA_*` code in CI output and want to understand it immediately, run `npx supaschema explain <code>` locally — no internet access required.
  </Tip>
</Accordion>

<Accordion title="selfcheck — Engine parity check">
  `selfcheck` compares supaschema's live-catalog extraction against the database engine's representation.

Use it when evaluating supaschema against an existing database or after upgrading supaschema.

```bash
npx supaschema selfcheck --database-url postgresql://postgres:postgres@localhost:54322/postgres
```

Flags: `--database-url <url>` (defaults to `SUPASCHEMA_DATABASE_URL` or the local Supabase stack).

  <Warning>
    `selfcheck` is a diagnostic tool, not a deployment gate. Normalization gaps it reports do not necessarily mean your migrations are incorrect — they mean supaschema's representation of a given object differs from the live catalog in some way. Review the output before deciding whether a gap matters for your use case.
  </Warning>
</Accordion>
