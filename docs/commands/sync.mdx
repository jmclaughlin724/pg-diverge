Use `sync` when you want a guarded Supabase CLI handoff.

With no apply flag, `sync` is a dry run. With `--local` or `--remote`, it reconciles history, checks pending migrations, then invokes the Supabase CLI.

## Use this when

- Supabase remains the migration runner.
- Pending files need `check` before apply.
- Ghost or out-of-order history should block deployment.
- A dry run should preview what the runner would apply.

## Run it

```bash
npx supaschema sync
npx supaschema sync --local
npx supaschema sync --remote
npx supaschema sync --env staging
```

`workflow.migration_sync` must allow explicit handoff. No config value makes apply automatic.

## Flags

<ParamField path="--migrations-dir" type="path">
  Directory containing migration files.
</ParamField>

<ParamField path="--database-url" type="url">
  Target database used for history reconciliation.
</ParamField>

<ParamField path="--local" type="boolean">
  Apply pending migrations with `supabase migration up`.
</ParamField>

<ParamField path="--remote" type="boolean">
  Push pending migrations with `supabase db push`.
</ParamField>

## Refusal cases

`sync` stops before handoff when:

- migration history has ghost versions;
- migration files are out of order;
- a pending migration fails `check`;
- the Supabase CLI is unavailable;
- `workflow.migration_sync` disables apply handoff.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Dry run passed, apply passed, or nothing was pending |
| `1` | Runtime failure |
| `2` | Gate failure or inconsistent migration history |
