The agent bundle gives coding agents the same migration workflow that humans use: edit declarative SQL, generate with `diff`, check replay safety, and never hand-edit generated migration files.

## Installed surfaces

The downloadable consumer agent bundle is intentionally narrow.

| Surface | Files |
| --- | --- |
| Shared install prompt | `.agents/prompts/supaschema-install.md` |
| Shared skill | `.agents/skills/supaschema` |
| Claude skill and rule | `.claude/skills/supaschema`, `.claude/rules/supaschema.md` |
| Claude hooks | `.claude/settings.json` entries for `supaschema hook schema-write` and `supaschema hook generated-migration-edit`, plus `.claude/hooks/guards/bash-policy-checks.mjs` and `.claude/hooks/sync-llm-on-claude-surface-change.mjs` |
| Codex rule mirror | `.codex/rules/supaschema.rules` |
| Codex hooks | `.codex/hooks.json` entries for `supaschema hook schema-write` and `supaschema hook generated-migration-edit`, plus `.codex/hooks/general-guard.mjs`, `.codex/hooks/guards/bash-policy-checks.mjs`, and `.codex/hooks/sync-llm-on-claude-surface-change.mjs` |

`postinstall` and `supaschema init` also write or merge hook registration files into the consuming project:

| Runtime | Generated registration  |
| ------- | ----------------------- |
| Claude  | `.claude/settings.json` |
| Codex   | `.codex/hooks.json`     |

`.claude/settings.json` is generated by `bin/scaffold.mjs`. `.codex/hooks.json` is the packaged consumer registration source and is merged into the consuming project by the same scaffolder.

The npm scaffold copies the packaged supaschema skill directories directly into both `.agents/skills/supaschema` and `.claude/skills/supaschema`. It does not run `npx skills` during install.

The managed `AGENTS.md` and `CLAUDE.md` addenda point agents to `.agents/prompts/supaschema-install.md` before setup or schema work. That prompt tells agents not to clone the supaschema source repository for normal use, lists the installed files, defines their post-install checks, and tells them how to report a clean install.

## npx skills lane

The public `npx skills` source is intentionally narrower than the npm setup surface:

```bash
npx skills add https://github.com/jmclaughlin724/supaschema/tree/main/skills/supaschema
```

Do not use the repository root as the Skills source. The Skills CLI scans standard agent skill directories, and this repository contains maintainer skill mirrors for developing supaschema itself.

That source mirrors `.claude/skills/supaschema/SKILL.md` into `skills/supaschema/SKILL.md`. It installs Agent Skill context only into the location selected by the Skills CLI. It does not install passive rule files, hook scripts, hook registration, config, or schema directories.

Rules and hooks are included by package install through the `postinstall` scaffold. If lifecycle scripts did not run, `supaschema init` through the same package manager's local runner uses the same scaffold and writes the same rule, skill, hook, config, and manifest surfaces.

## Hook behavior

The installed hooks enforce supaschema migration policy and a small Bash safety policy:

| Hook | Event | Purpose |
| --- | --- | --- |
| `supaschema hook generated-migration-edit` | `PreToolUse` | Blocks edits to generated migration SQL when the lineage marker is present. |
| `bash-policy-checks.mjs` / `general-guard.mjs` | `PreToolUse` for Bash | Blocks secret argv and secret env-file reads, raw SQL DDL through Bash, destructive git shortcuts, and `rm -rf` equivalents. Plain recursive `rm -r` is not blocked by this generic policy. |
| `supaschema hook schema-write` | `PostToolUse` | Watches schema-tree SQL writes. By default it runs `supaschema diff` then `supaschema check`; when config enables automatic sync and every selected target is resolved and approved, it delegates to `supaschema sync`. |
| `sync-llm-on-claude-surface-change.mjs` | Claude `PostToolBatch`, Codex `Stop` | Keeps the installed `.agents` skill and Codex rule/hook mirrors aligned when the consumer edits the shipped `.claude` supaschema rule or skill. |

`supaschema hook schema-write` triggers the default migration workflow after configured schema files are edited. It writes the migration when `workflow.schema_diff` is `"on_schema_write"` and runs the replay-safety check when `workflow.migration_check` is `"after_schema_diff"`. If `workflow.migration_sync` allows automatic sync, the hook first confirms the selected `sync.targets` are `mode: "auto"`, database URL references resolve, and any remote target has its configured approval variable set. Only then does it call `supaschema sync`, which owns diff, generated outputs, type/RLS safety gates, apply, and target history reconciliation.

If config or approval does not permit automatic sync, the hook stays on the non-mutating diff/check lane. If `check` or `sync` fails, the hook emits continuation feedback so Claude or Codex investigates the root source, searches for correlated migration failures, fixes the canonical owner, and reruns the failing command.

## Repo-local tooling

Maintainer Claude/Codex optimization infrastructure is not part of the download or install scaffold by default.

Keep these repo-local unless the consumer contract explicitly changes:

- `.claude/hooks/context-*`
- `.codex/hooks/context-*`
- `scripts/agent-hooks/**`
- optimizer skills
- internal rules
- `.claude/agents/**`
- `.codex/agents/**`
- `.codex/config.toml`

If one of these surfaces becomes part of the consumer contract, update the package allowlist, scaffold, package tests, and [Package Boundary](/reference/package-boundary) in the same change.
