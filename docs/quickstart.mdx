---
title: "Quickstart"
description: "Install supaschema, write a declarative schema file, generate a replay-safe PostgreSQL migration from explicit offline sources, and validate it."
---

This guide generates one replay-safe migration from one schema file.

The examples use the neutral paths:

- schema files: `database/schemas`
- migrations: `database/migrations`

If install selected provider-specific paths, use the values in `supaschema.config.json` instead.

<Tip>
  Keep this page open while you work. Each step has one command or one file edit.
</Tip>

<Steps>
  <Step title="Install">
    Install supaschema as a dev dependency:

    ```bash
    npm install supaschema
    ```

    Check the binary:

    ```bash
    npx supaschema --version
    ```
  </Step>

  <Step title="Write schema">
    Create the schema folder:

    ```bash
    mkdir -p database/schemas
    ```

    Create `database/schemas/app.sql`:

    ```sql
    -- database/schemas/app.sql

    CREATE SCHEMA app;

    CREATE TABLE app.accounts (
      id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
      name text NOT NULL
    );

    ALTER TABLE app.accounts ENABLE ROW LEVEL SECURITY;

    CREATE POLICY accounts_select ON app.accounts
      FOR SELECT
      TO public
      USING (true);
    ```

    <Tip>
      You can split your schema across multiple files. supaschema reads `.sql` files in lexicographic order, so keep dependencies earlier by file name.
    </Tip>

    Your schema files are the source of truth. You edit them directly. supaschema writes the migration.
  </Step>

  <Step title="Generate">
    Generate the migration:

    ```bash
    npx supaschema diff --from git:HEAD --to dir:database/schemas
    ```

    supaschema compares `git:HEAD` to your edited schema files. It writes one timestamped migration.

    You will see output similar to:

    ```
    ✔ Parsed schema tree (3 objects)
    ✔ Resolved migrations history (0 migrations)
    ✔ Computed diff (4 operations)

    Created: database/migrations/20240101120000_migration.sql
    ```

    Open the generated file and review it. Every generated statement is guarded so the migration is safe to re-run.

    ```sql
    -- database/migrations/20240101120000_migration.sql
    -- Generated by supaschema x.y.z.
    -- Operations: 1 create schema, 1 create table, 1 enable rls, 1 create policy
    -- supaschema: lineage from=0000000000000000... to=4db806bc9b786ea2...
    SET lock_timeout = '5s';

    CREATE SCHEMA IF NOT EXISTS app;

    CREATE TABLE IF NOT EXISTS app.accounts (
        id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
        name text NOT NULL
    );

    DO $supaschema$
    BEGIN
      IF NOT EXISTS (SELECT 1 FROM pg_catalog.pg_constraint c
                     JOIN pg_catalog.pg_class t ON t.oid = c.conrelid
                     WHERE t.relname = 'accounts' AND c.conname = 'accounts_pkey') THEN
        ALTER TABLE app.accounts ADD CONSTRAINT accounts_pkey PRIMARY KEY (id);
      END IF;
    END
    $supaschema$;

    ALTER TABLE app.accounts ENABLE ROW LEVEL SECURITY;

    DROP POLICY IF EXISTS accounts_select ON app.accounts;

    CREATE POLICY accounts_select ON app.accounts
        FOR SELECT
        TO public
        USING (true);
    ```

    <Tip>
    Use explicit sources when you want the run to stay offline:

      ```bash
      npx supaschema diff --from git:HEAD --to dir:database/schemas
      ```
    </Tip>
  </Step>

  <Step title="Check">
    Check the migration before applying it:

    ```bash
    npx supaschema check database/migrations/20240101120000_migration.sql
    ```

    A passing check looks like:

    ```
    ✔ Parsed 4 statements
    ✔ No destructive operations detected
    ✔ Migration is replay-safe

    database/migrations/20240101120000_migration.sql — OK
    ```

    <Warning>
      If `check` reports issues, review the flagged statements before applying the migration. supaschema fails closed when it cannot prove safety.
    </Warning>
  </Step>

  <Step title="Apply">
    supaschema generates migrations. Your normal runner applies them.

    For a direct `psql` apply:

    ```bash
    psql "$DATABASE_URL" -f database/migrations/20240101120000_migration.sql
    ```

    In a Supabase project, generated files in `supabase/migrations` can be applied with the Supabase CLI:

    ```bash
    supabase db push
    ```

    supaschema owns generation and proof. Your runner owns application.

    <Note>
      supaschema never applies migrations to your target database. It also does not need a shadow database for file, Git, dump, or catalog sources.
    </Note>
  </Step>

  <Step title="Generate types">
    Generate TypeScript and Zod output:

    ```bash
    npx supaschema types
    ```

    The output comes from your schema files. It does not require a live database.

    ```
    ✔ Parsed schema tree (3 objects)
    ✔ Generated TypeScript types

    database.types.ts
    database.zod.ts
    ```
  </Step>
</Steps>
