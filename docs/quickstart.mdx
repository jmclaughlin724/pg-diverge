---
title: "Quickstart"
description: "Install supaschema, write a declarative schema file, generate a replay-safe PostgreSQL migration from explicit offline sources, and validate it."
---

supaschema works with plain PostgreSQL and with managed PostgreSQL platforms, including Supabase, Neon, RDS/Aurora PostgreSQL, Cloud SQL, AlloyDB, and Azure PostgreSQL. This guide uses the neutral PostgreSQL layout created by install: `database/schemas` for declarative SQL and `database/migrations` for generated migrations. If install selected provider-specific paths, use the `schemaPaths` and `migrationsDir` values in `supaschema.config.json` instead.

<Steps>
  <Step title="Install">
    supaschema requires **Node.js 22.12 or later** and targets **PostgreSQL 15 or later**. Install it as a dev dependency in your project:

    ```bash
    npm install --save-dev supaschema
    ```

    Verify the installation:

    ```bash
    npx supaschema --version
    ```
  </Step>

  <Step title="Write schema">
    Create your first schema file:

    ```bash
    mkdir -p database/schemas
    ```

    Then create `database/schemas/001_app.sql` with the following content:

    ```sql
    -- database/schemas/001_app.sql

    CREATE SCHEMA app;

    CREATE TABLE app.accounts (
      id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
      name text NOT NULL
    );

    ALTER TABLE app.accounts ENABLE ROW LEVEL SECURITY;

    CREATE POLICY accounts_select ON app.accounts
      FOR SELECT
      TO public
      USING (true);
    ```

    <Tip>
      You can split your schema across as many files as you like. supaschema processes all `.sql` files in your configured `schemaPaths` in lexicographic order. Prefix filenames with a numeric sequence (e.g. `001_`, `002_`) to control load order explicitly.
    </Tip>

    Your schema files are the single source of truth. You edit them directly — you never write migration SQL by hand.
  </Step>

  <Step title="Generate">
    With your schema file in place, run `diff` to generate a migration:

    ```bash
    npx supaschema diff --from git:HEAD --to dir:database/schemas
    ```

    supaschema compares the schema files committed at `HEAD` against your edited declarative schema files in `database/schemas` and writes a new timestamped migration file to `database/migrations`.

    You will see output similar to:

    ```
    ✔ Parsed schema tree (3 objects)
    ✔ Resolved migrations history (0 migrations)
    ✔ Computed diff (4 operations)

    Created: database/migrations/20240101120000_migration.sql
    ```

    The generated migration file contains only the SQL needed to move from your current state to your desired state. Every statement is guarded so the migration is safe to re-run. Open it to review the output:

    ```sql
    -- database/migrations/20240101120000_migration.sql
    -- Generated by supaschema x.y.z.
    -- Operations: 1 create schema, 1 create table, 1 enable rls, 1 create policy
    -- supaschema: lineage from=0000000000000000... to=4db806bc9b786ea2...
    SET lock_timeout = '5s';

    CREATE SCHEMA IF NOT EXISTS app;

    CREATE TABLE IF NOT EXISTS app.accounts (
        id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
        name text NOT NULL
    );

    DO $supaschema$
    BEGIN
      IF NOT EXISTS (SELECT 1 FROM pg_catalog.pg_constraint c
                     JOIN pg_catalog.pg_class t ON t.oid = c.conrelid
                     WHERE t.relname = 'accounts' AND c.conname = 'accounts_pkey') THEN
        ALTER TABLE app.accounts ADD CONSTRAINT accounts_pkey PRIMARY KEY (id);
      END IF;
    END
    $supaschema$;

    ALTER TABLE app.accounts ENABLE ROW LEVEL SECURITY;

    DROP POLICY IF EXISTS accounts_select ON app.accounts;

    CREATE POLICY accounts_select ON app.accounts
        FOR SELECT
        TO public
        USING (true);
    ```

    <Tip>
    Use explicit sources when you want the whole run to stay offline:

      ```bash
      npx supaschema diff --from git:HEAD --to dir:database/schemas
      ```
    </Tip>
  </Step>

  <Step title="Check">
    Before applying the migration, use `check` to validate it:

    ```bash
    npx supaschema check database/migrations/20240101120000_migration.sql
    ```

    `check` parses the migration using the PostgreSQL WASM parser and verifies its structural correctness and safety. A passing check looks like:

    ```
    ✔ Parsed 4 statements
    ✔ No destructive operations detected
    ✔ Migration is replay-safe

    database/migrations/20240101120000_migration.sql — OK
    ```

    <Warning>
      If `check` reports any issues, review the flagged statements before applying the migration. supaschema will never silently suppress warnings that could result in data loss.
    </Warning>
  </Step>

  <Step title="Apply">
    supaschema generates migrations but never applies them to a target database directly. Use your normal PostgreSQL migration runner. For a direct `psql` apply:

    ```bash
    psql "$DATABASE_URL" -f database/migrations/20240101120000_migration.sql
    ```

    In a Supabase project, generated files in `supabase/migrations` can be applied with the Supabase CLI:

    ```bash
    supabase db push
    ```

    This keeps your existing deployment workflow intact. supaschema slots in as the migration *generation* step; your runner handles the *application* step.

    <Note>
      supaschema never applies migrations to your database or requires a shadow database. When you pass file, git, dump, or catalog sources as shown above, migration generation is entirely offline; omit `--from` only when you intentionally want the configured live database to be the applied-state source.
    </Note>
  </Step>

  <Step title="Generate types">
    Once your schema is defined, you can generate TypeScript types from it:

    ```bash
    npx supaschema types
    ```

    This produces a type file derived from your declarative schema, giving you end-to-end type safety from database schema to application code — no separate `supabase gen types` step required against a live database.

    ```
    ✔ Parsed schema tree (3 objects)
    ✔ Generated TypeScript types

    database.types.ts
    database.zod.ts
    ```
  </Step>
</Steps>
