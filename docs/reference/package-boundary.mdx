Use this page when changing release packaging, agent bundle files, or install-time setup.

## Decision rule

supaschema uses the `files` allowlist in `package.json` as the npm package boundary.

There is intentionally no root `.npmignore`.

<Note>
  npm treats `files` as an allowlist. A root `.npmignore` is a denylist. This
  repository has many maintainer-only support files, so allowing known package
  contents is safer than trying to exclude everything that should not publish.
</Note>

## Three surfaces

| Surface | Source of truth | Purpose |
| --- | --- | --- |
| npm tarball | `package.json` `files` | Files downloaded into `node_modules/supaschema` |
| Consumer setup | `postinstall` | Files written or merged into the installing project |
| Maintainer workspace | git-tracked repo files outside the package allowlist | Tooling for developing supaschema itself |

The npm tarball and consumer setup are not the same thing. The tarball is what
npm downloads. The installer is the script that uses selected tarball files and
generated templates to prepare the consuming project.

## npm package

The package allowlist includes runtime and public-support assets: the built CLI
and library, config schema, docs, examples, public benchmark/corpus assets, and
the supaschema agent bundle.

Do not add broad repo directories to the allowlist just because a single file is
needed. Add the narrowest file or directory that matches the consumer contract.

Generated build caches must not live inside an allowlisted directory: a broad
entry like `dist` ships everything beneath it, so write a `tsBuildInfoFile` to
`.tmp/` rather than `dist/`. `tests/package-contents.test.ts` fails if any
`.tsbuildinfo`, source file, or maintainer tooling reaches the tarball.

## Consumer setup

The installer owns one-step setup for consuming projects. The install contents
list lives in [Introduction](/introduction#what-gets-installed); keep it there
instead of duplicating it across release and packaging references.

Do not copy maintainer workspace tooling into consumer projects unless the
consumer contract explicitly changes and package tests are updated at the same
time.

## Maintainer workspace

Repo-local editor, language-server, Python, MCP, Code Atlas, FastMCP, lint,
test, guard, and release tooling is for developing supaschema itself.

These files stay out of the package allowlist unless they become runtime product
assets or consumer install outputs.

## Why not .npmignore?

npm supports `.npmignore`, but it is a blocklist. Blocklists are fragile in a
repo that has many development surfaces and only a small, deliberate consumer
surface.

npm also falls back to `.gitignore` when `.npmignore` is missing and no `files`
allowlist is present. Because supaschema does have a `files` allowlist, the root
package boundary should stay in `package.json`.

## Verification

Run these checks when packaging or installer behavior changes:

```bash
npm pack --dry-run --json
npm run check:package
npm run guard
npx vitest run tests/editor-surfaces.test.ts tests/database-url.test.ts
```

The dry-run tarball is the authoritative preview of what npm will publish.
