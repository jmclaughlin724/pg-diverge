The day-to-day migration workflow is one command:

```bash
npx supaschema diff
```

That command reads the configured source, reads the target declarative SQL tree, plans the change, renders the migration, writes it to the configured migration directory, and refreshes configured TypeScript and Zod outputs.

```text
database or migration state + declarative SQL tree
  -> extract structured models
  -> plan safe operations
  -> render replay-safe SQL
  -> write migration + generated outputs
```

## What happens inside

<Steps>
  <Step title="Extract">
    supaschema loads both sides into structured PostgreSQL models. SQL
    understanding comes from parser-backed models, not raw text comparison.
  </Step>
  <Step title="Plan">
    The planner compares tables, constraints, indexes, functions, triggers,
    views, policies, grants, foreign data wrappers, comments, and supported
    extension ownership. Unsupported and provider-owned surfaces fail closed
    instead of being guessed.
  </Step>
  <Step title="Render">
    The renderer emits deterministic SQL with idempotent guards, lock and
    statement timeouts, lineage markers, and destructive-intent checks.
  </Step>
  <Step title="Refresh generated outputs">
    Configured TypeScript and Zod outputs are generated from the same
    declarative tree as the migration, keeping runtime validators aligned with
    schema intent.
  </Step>
</Steps>

## Safety gates

`supaschema diff` is the generator. The same package also includes explicit gates for CI and release lanes:

<CardGroup cols={2}>
  <Card title="Check" icon="shield-check" href="/commands/check">
    Replays generated migrations and blocks unsafe or out-of-contract SQL.
  </Card>
  <Card title="Verify" icon="repeat-2" href="/commands/verify">
    Proves the newest pending migration can apply twice against a disposable
    database.
  </Card>
  <Card title="Sync" icon="refresh-cw" href="/commands/sync">
    Runs diff, generated-output refresh, safety gates, target reconciliation,
    and selected runner apply.
  </Card>
  <Card title="CI drift gate" icon="git-branch" href="/guides/ci-gate">
    Runs `supaschema diff --fail-on-diff --quiet` to fail when the schema tree
    and migrations drift.
  </Card>
</CardGroup>

Use the [corpus oracle](/guides/corpus-oracle) for real-world reconvergence fixtures, and use [ORM-free applications](/concepts/orm-free-applications) to wire generated TypeScript and Zod outputs into application boundaries.

In projects with the installed coding-agent hooks, schema-tree edits trigger `diff` and `check` automatically after the write. The agent still treats generated migrations as output and reports the migration or diagnostic instead of editing generated SQL.

## Apply orchestration

supaschema keeps generation and deployment as separate workflow stages, but `sync` is the built-in orchestration path. `diff` writes the migration; `sync` can generate or reuse pending SQL, refresh generated outputs, reconcile each selected target, check pending migrations, run deploy safety gates, and apply through the configured runner.

For plain PostgreSQL and hosted PostgreSQL providers, `sync` can use the direct PostgreSQL runner when a target database URL is configured or passed explicitly. For Supabase projects, `sync` can use the Supabase CLI adapter. The installed default lets target config decide selection, so day-to-day apply is `supaschema sync` and every `sync.targets.<name>` entry with `mode: "auto"` is selected. Remote targets use the same `mode` rule and also require their approval environment variable. `--target <name>` is the explicit override path for one configured target.

Teams that already use `psql`, a deployment job, Terraform-controlled operations, Flyway, Liquibase, a platform migration service, or another reviewed SQL runner can keep that external apply step. That is an operational boundary, not a reason to duplicate schema ownership or generated types in an ORM.

<Note>
  `sync` is the canonical package-owned apply pipeline. External runners are a
  deliberate integration choice when a team already has a separate deployment
  owner.
</Note>
