The day-to-day migration workflow is one command:

```bash
npx supaschema diff
```

That command reads the configured source, reads the target declarative SQL tree, plans the change, renders the migration, writes it to the configured migration directory, and refreshes configured TypeScript and Zod outputs.

```text
database or migration state + declarative SQL tree
  -> extract structured models
  -> plan safe operations
  -> render replay-safe SQL
  -> write migration + generated outputs
```

## What happens inside

<Steps>
  <Step title="Extract">
    supaschema loads both sides into structured PostgreSQL models. SQL
    understanding comes from parser-backed models, not raw text comparison.
  </Step>
  <Step title="Plan">
    The planner compares tables, constraints, indexes, functions, triggers,
    views, policies, grants, publications, subscriptions, storage objects, and
    supported extension ownership.
  </Step>
  <Step title="Render">
    The renderer emits deterministic SQL with idempotent guards, lock and
    statement timeouts, lineage markers, and destructive-intent checks.
  </Step>
  <Step title="Refresh generated outputs">
    Configured TypeScript and Zod outputs are generated from the same
    declarative tree as the migration, keeping runtime validators aligned with
    schema intent.
  </Step>
</Steps>

## Safety gates

`supaschema diff` is the generator. The same package also includes explicit gates for CI and release lanes:

<CardGroup cols={2}>
  <Card title="Check" icon="shield-check" href="/commands/check">
    Replays generated migrations and blocks unsafe or out-of-contract SQL.
  </Card>
  <Card title="Verify" icon="repeat-2" href="/commands/verify">
    Proves the newest pending migration can apply twice against a disposable
    database.
  </Card>
  <Card title="CI drift gate" icon="git-branch" href="/guides/ci-gate">
    Runs `supaschema diff --fail-on-diff --quiet` to fail when the schema tree
    and migrations drift.
  </Card>
  <Card title="Corpus oracle" icon="database-zap" href="/guides/corpus-oracle">
    Tests real-world dirty catalogs for reconvergence when a database is
    reachable.
  </Card>
</CardGroup>

In projects with the installed coding-agent hooks, schema-tree edits trigger `diff` and `check` automatically after the write. The agent still treats generated migrations as output and reports the migration or diagnostic instead of editing generated SQL.

## Apply handoff

supaschema intentionally separates generation from deployment. `diff` writes the migration; your runner applies it.

For plain PostgreSQL and hosted PostgreSQL providers, apply the checked SQL with the runner you already use: `psql`, a deployment job, Terraform-controlled operations, Flyway, Liquibase, a platform migration service, or another reviewed SQL runner.

For Supabase projects, `supaschema sync` is the optional explicit handoff lane. With no apply flag it is a dry run. With `--local` or `--remote`, it runs status and replay-safety gates before delegating the apply or deploy step to the Supabase CLI, and only when the configured workflow allows explicit apply handoff.

<Note>
  The common workflow is still one generation command: `npx supaschema diff`.
  `check`, `verify`, and `sync` are optional gates for CI, release, and
  operator-controlled deployment.
</Note>
