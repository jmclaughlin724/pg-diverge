supaschema is a Node.js CLI and library for generating deterministic PostgreSQL and Supabase migrations from declarative SQL schema files. You keep the desired schema in SQL, run `supaschema diff`, and review the generated replay-safe migration before your usual migration runner applies it.

## What is supaschema?

supaschema is a generator, checker, and verifier:

- `diff` compares schema sources and writes a migration.
- `check` statically validates migration SQL for replay safety and lock hazards.
- `verify` applies a migration twice in disposable databases and checks convergence.
- `types` emits Supabase-compatible TypeScript types and Zod validators from the declarative tree.

It can read schema state from SQL files, Git refs, live databases, SQL dumps, or saved catalog snapshots. Generation from files or Git refs does not require Docker, a shadow database, or a live PostgreSQL connection.

## What gets installed?

Installing `supaschema` gives a project everything a human or coding agent needs to start generating migrations. It creates config when no config exists, scans for existing schema and migrations folders, and installs the bundled Claude/Codex-compatible agent rule, skill, and hooks. It does not edit schema files, generate migrations, or connect to a database.

The package includes:

- the `supaschema` CLI for setup, diff generation, checks, verification, and type generation;
- typed ESM library exports for scripts, tests, and custom tooling;
- the PostgreSQL parser and SQL deparser dependencies needed for AST-based schema reads;
- the JSON Schema for editor validation of `supaschema.config.json`;
- a `supaschema.config.json` when the project does not already define config;
- the bundled coding-agent instructions, rules, skills, and hooks for Claude and Codex-compatible agents.

After install, an agent can follow the same loop a human would: edit declarative SQL, run `diff`, run `check`, and only apply through your normal migration runner when asked.

## Why supaschema?

Database-backed diff workflows are slow and easy to mistrust when schemas grow. They also miss classes of changes that matter in Supabase projects, especially Row Level Security policy body changes.

supaschema uses PostgreSQL parse trees through `libpg-query` and structured schema models instead. That design gives you:

- **Offline migration generation** from committed SQL files or Git refs.
- **Replay-safe SQL** with guarded creates and catalog-checked operations.
- **Structural policy comparison** for RLS policies, not name-only matching.
- **Fast type generation** from the declarative tree, without waiting for a deployed database.
- **CI-friendly proofs** through `check`, `verify`, drift gates, and diagnostics.

## How it fits

supaschema does not replace your migration runner. In a Supabase project, the normal flow is:

1. Edit the declarative schema files.
2. Generate a migration with `supaschema diff`.
3. Validate it with `supaschema check` and, when possible, `supaschema verify`.
4. Apply it with your runner, such as `supabase db push`.

The optional `supaschema sync` command is an explicit apply gate: without `--local` or `--remote` it is a dry run, and with an apply flag it delegates to the Supabase CLI after status and replay-safety checks.
