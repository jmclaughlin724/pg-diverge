supaschema generates PostgreSQL migrations from declarative SQL files.

You edit the schema you want. supaschema writes the migration, checks that it is replay-safe, and can prove it in disposable databases.

<Info>
  If you only remember one thing: edit the configured schema tree, then run
  `supaschema diff` and `supaschema check`.
</Info>

## What is supaschema?

supaschema is a Node.js CLI and library with four core jobs:

- `diff` compares schema sources and writes a migration.
- `check` validates migration SQL for replay safety and lock hazards.
- `verify` applies a migration twice in disposable databases and checks convergence.
- `types` emits TypeScript types and Zod validators from the schema tree.

It can read state from SQL files, Git refs, live databases, SQL dumps, or saved catalog snapshots.

File and Git sources do not need Docker, a shadow database, or a live PostgreSQL connection.

## What gets installed?

Installing `supaschema` prepares the project in one step. When npm does not run install scripts (npm v12 ignores dependency install scripts by default), `npx supaschema init` performs the same setup.

It does not edit schema files. It does not generate migrations. It does not connect to a database.

The package includes:

- the `supaschema` CLI;
- typed ESM library exports;
- PostgreSQL parser and SQL deparser dependencies;
- JSON Schema validation for `supaschema.config.json`;
- a config file when the project does not already have one, including `adapter`, `workflow`, `schemaPaths`, `sources`, `migrationsDir`, `typesFile`, `zodFile`, and `environments`;
- the narrow [supaschema consumer agent bundle](/coding-agents/agent-bundle): Claude/Codex-compatible supaschema rules, skills, migration-policy hooks, sync hooks, and agent guidance.

Install also scans for existing schema and migration folders. See [Setup](/setup) for the exact path rules.

The repository also has maintainer-only workspace tooling for developing supaschema itself, such as VS Code settings, Postgres Language Server config, Python workspace config, MCP research servers, Code Atlas, FastMCP checks, Claude/Codex context-enforcement hooks, and optimizer skills. Those files are not consumer install outputs and are not copied into projects by package install.

## Why supaschema?

Database-backed diff workflows slow down as schemas grow. They also make it easy to miss changes that matter, such as Row Level Security policy body changes.

supaschema uses PostgreSQL parse trees through `libpg-query` and structured schema models. That gives you:

- offline migration generation from SQL files or Git refs;
- replay-safe SQL with guarded creates;
- structural RLS policy comparison;
- type generation before deploy;
- CI gates through `check`, `verify`, drift detection, and diagnostics.

## How it fits

supaschema does not replace your migration runner.

The normal flow is:

1. Edit the declarative schema files.
2. Generate a migration with `supaschema diff`.
3. Validate it with `supaschema check` and, when possible, `supaschema verify`.
4. Apply it with your runner.

Common runners include `psql`, a platform deployment job, and `supabase db push`.

<Note>
  `supaschema sync` is a Supabase-specific apply gate. With no apply flag, it is
  a dry run. With `--local` or `--remote`, it delegates to the Supabase CLI
  after safety checks only when `workflow.migration_sync` allows explicit apply
  handoff.
</Note>
