Setup is completed by package install.

Run:

```bash
npm install supaschema
```

The installer prepares the project once. It does not generate or apply a migration.

<Info>
  If you need to change paths later, edit `schemaPaths`, `migrationsDir`, `typesFile`, or `zodFile` in `supaschema.config.json`.
</Info>

This page covers path selection, agent addendum behavior, setup checks, and where detailed configuration lives. For the package contents installed in that step, see [What gets installed?](/introduction#what-gets-installed).

## Path selection

Install scans the repository before writing config.

The path decision is:

- one detected schema folder and one detected migrations folder are used automatically;
- if a provider marker is present and no existing schema or migrations folder is found, install uses that provider's default folders;
- otherwise the neutral PostgreSQL layout is `database/schemas` and `database/migrations`;
- if multiple candidates exist, install records them in `.supaschema/install.json`;
- in an interactive terminal, install can ask for the paths immediately.

<Warning>
  Do not run the first `diff` from a guessed path. If `.supaschema/install.json` says `pathConfirmationNeeded: true`, confirm the intended paths first.
</Warning>

| Provider marker | Schema path | Migrations path |
| --- | --- | --- |
| `supabase/config.toml` | `supabase/schemas` | `supabase/migrations` |
| `neon.toml`, `.neon/project.json`, `.neon/config.json`, or Neon references in `drizzle.config.*` | `neon/schemas` | `neon/migrations` |
| RDS/Aurora markers in Terraform, CloudFormation/SAM, CDK, SST, or Serverless config | `aws-postgresql/schemas` | `aws-postgresql/migrations` |
| Cloud SQL markers in Terraform, Cloud Build, or App Engine config | `cloud-sql/schemas` | `cloud-sql/migrations` |
| AlloyDB markers in Terraform, Cloud Build, or App Engine config | `alloydb/schemas` | `alloydb/migrations` |
| Azure PostgreSQL markers in Terraform, Bicep, ARM, or Azure Developer CLI config | `azure-postgresql/schemas` | `azure-postgresql/migrations` |

When no existing folders are found, generic PostgreSQL projects use `database/schemas` and `database/migrations`. The full generated config shape is defined in [Configuration](/configuration/config-file#generated-config).

All providers use `adapter: "auto"`. Provider detection only seeds paths; managed schema protection, transaction behavior, type outputs, and environment references are configured with explicit fields in `supaschema.config.json`.

Commit this file. It keeps developers, CI, and coding agents on the same paths.

If the config is deleted later, run `npx supaschema init` to recreate it.

## Agent addendum

Install updates `AGENTS.md` and `CLAUDE.md` by replacing only the managed block between these markers:

```text
<!-- supaschema:agent-guidance:start -->
<!-- supaschema:agent-guidance:end -->
```

Existing content outside the markers is preserved.

## Check setup

Run `doctor` when you want a one-page environment check:

```bash
npx supaschema doctor
```

`doctor` checks:

- Node version;
- parser load;
- config validity;
- database URL resolution;
- database reachability when a URL is available;
- `CREATEDB` capability for verification;
- migration history;
- declarative schema tree.
