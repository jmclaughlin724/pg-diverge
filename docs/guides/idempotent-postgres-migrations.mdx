# Idempotent PostgreSQL migrations

An idempotent PostgreSQL migration can be retried safely. If a deploy crashes after part of the file ran, the runner can execute the file again without failing on objects that already exist.

`supaschema` generates replay-safe migrations by construction and verifies that migration files stay safe before they are applied.

## Why replay safety matters

Production migration runners can be interrupted by network failures, lock timeouts, crashed deploy jobs, or partial rollbacks. A migration that contains unguarded statements such as `CREATE TABLE`, `CREATE INDEX`, or `ALTER TABLE ADD COLUMN` may succeed once and fail on retry.

Replay-safe SQL avoids that class of failure.

## What supaschema emits

`supaschema` uses the safest available PostgreSQL form for each operation:

```sql
CREATE TABLE IF NOT EXISTS app.accounts (
  id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL
);
```

For operations without a simple `IF NOT EXISTS` form, it emits catalog-checked blocks:

```sql
DO $supaschema$
BEGIN
  IF NOT EXISTS (
    SELECT 1
    FROM pg_catalog.pg_constraint c
    WHERE c.conname = 'accounts_pkey'
  ) THEN
    ALTER TABLE app.accounts ADD CONSTRAINT accounts_pkey PRIMARY KEY (id);
  END IF;
END
$supaschema$;
```

The exact generated SQL depends on the object and dependency order, but the goal is the same: a second apply should converge instead of fail.

## Check existing migrations

Run:

```bash
npx supaschema check
```

`check` parses migration SQL and flags unguarded DDL, unsafe `CASCADE`, session-level hazards, lock risks, and unapproved destructive operations.

For GitHub Actions annotations:

```bash
npx supaschema check --reporter github
```

For code scanning:

```bash
npx supaschema check --reporter sarif
```

## Prove replay safety with verify

When a disposable database is available, run:

```bash
npx supaschema verify
```

`verify` applies the newest pending migration, applies it again, and compares the final catalog to the declared target. That catches problems that static analysis cannot prove alone.

## Destructive changes are not idempotency shortcuts

Do not use broad destructive hints to make a diff pass. Drops and type rewrites require explicit review because replay-safe SQL can still be logically unsafe when it deletes data or weakens constraints.

Use [destructive hints](/configuration/hints) only for exact reviewed object keys.
