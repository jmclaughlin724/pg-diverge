Row Level Security policy predicates are access-control logic. A migration generator must detect changes to `USING` and `WITH CHECK` expressions, because the policy name can stay the same while tenant isolation changes.

`supaschema` compares RLS policy definitions structurally and surfaces predicate changes as migration operations.

## The risk

In a Supabase application, a policy like this may be the tenant boundary:

```sql
CREATE POLICY invoices_select ON app.invoices
  FOR SELECT
  TO authenticated
  USING (tenant_id = auth.uid());
```

If the policy body changes, review must see the change. Treating two policies as equal because their names match can hide a regression or omit a needed tightening.

## How supaschema compares policies

`supaschema` parses policy statements with PostgreSQL's parser and compares the normalized structure. A changed `USING` expression, changed `WITH CHECK` expression, changed command, changed roles, or changed permissive/restrictive mode is a real schema change.

That means this edit is not ignored:

```sql
-- before
USING (true)

-- after
USING (tenant_id = auth.uid())
```

The generated migration will include the policy change and `check` will include it in the review surface.

## Recommended workflow

Keep RLS policies in the declarative tree next to the tables they protect:

```text
supabase/schemas/
  020_invoices.sql
  021_invoices_policies.sql
```

Then run:

```bash
npx supaschema diff
npx supaschema check
npx supaschema verify
```

In CI, use `diff --fail-on-diff` so drift between the database and policy files blocks the merge:

```bash
npx supaschema diff --fail-on-diff --quiet
```

## What reviewers should look for

Review RLS migrations like application security changes:

- Does every tenant-scoped table have RLS enabled?
- Did a `USING` predicate broaden access?
- Did a `WITH CHECK` predicate weaken write isolation?
- Did role coverage change?
- Did the migration drop and recreate a policy instead of altering the intended object?

`supaschema` makes those changes visible; the final security decision still belongs to the reviewer.
