Deterministic, replay-safe PostgreSQL and Supabase migrations from declarative SQL trees — a TypeScript CLI and library with no Docker, no shadow database, and no diff-engine container.

**At a glance**, measured on identical fixtures and verified by applying every generated migration twice ([benchmarks](#benchmarks)):

|  | pg-diverge | Supabase CLI engines (all five) |
| --- | --- | --- |
| Diff latency, 1 → 2,500 tables (~17,500 objects) | 0.2s → 2.7s | ~7.5s → ~5 minutes |
| Generated SQL survives a second apply | every fixture | fails on column/index changes |
| Diff content vs intended change (F1) | 1.000 on every scored fixture | 0.982–0.999 (each missed a policy change) |
| Infrastructure per diff | none — pure TypeScript + WASM | Docker shadow database |
| Ambiguous change (rename, drop, type change) | blocked until explicitly hinted | inferred or dropped silently |

## The Problem

Your schema tree says what the database _should_ look like. A diff engine turns that into a migration — and today's engines fail in four ways:

- **Slow.** Every diff replays the entire schema into a throwaway Docker database: ~7.5 seconds for one table, ~5 minutes at 2,500.
- **Not replayable.** The generated SQL fails the second time it runs. One crashed deploy and you're hand-editing migrations.
- **Guesses.** Renames inferred from name similarity. Whole tables replaced to change one column.
- **Unproven.** The output is never executed the way `supabase db push` runs it — one transaction per file — so it can pass review and still fail in production.

pg-diverge fixes all four.

## One Command

```bash
npx pg-diverge diff
```

Edit your tree, run that. It diffs your applied state (the resolved database, falling back to `git:HEAD`) against your schema tree (`supabase/schemas`) and writes the migration into `supabase/migrations`. Defaults print to stderr; every flag overrides.

```sql
-- Generated by pg-diverge 0.1.0.
-- Operations: 1 create constraint, 1 create table, 1 drop function,
--             1 replace policy, 1 replace view, ...
-- pg-diverge: lineage from=a145201bcaa397f6... to=4db806bc9b786ea2...
SET lock_timeout = '5s';
SET statement_timeout = '60s';

DROP FUNCTION IF EXISTS "app"."legacy_ping"();

CREATE TABLE IF NOT EXISTS app.audit_events (
  id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
  account_id bigint NOT NULL,
  event_name text NOT NULL
);

DO $pg_diverge$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_catalog.pg_constraint c ...) THEN
    ALTER TABLE app.audit_events ADD CONSTRAINT audit_events_pkey PRIMARY KEY (id);
  END IF;
END
$pg_diverge$;
```

Real output, trimmed from the repo's `basic` fixture: replay-guarded statements in dependency order, a lock-bounding timeout preamble, and a lineage header chaining the next migration to this one. Destructive or ambiguous changes refuse to render until the object is named in `hints.destructive` — the diff fails closed instead of guessing.

## What You Get

- **Idempotent, pre-normalized SQL by construction.** Every statement is guard-rendered (`IF NOT EXISTS`, `DROP ... IF EXISTS`, `pg_catalog`-checked `DO` blocks), and `normalize: "deparse"` optionally rewrites object SQL into canonical PostgreSQL form — fidelity-gated per object, so formatting never affects identity. Migrations survive crashed deploys and replayed environments.
- **Accuracy you can score.** Diff content is measured against ground-truth change manifests, not eyeballed: F1 1.000 on every scored fixture, where each shadow-database engine silently missed an RLS policy change ([why that matters](#accuracy-the-diff-says-what-you-meant)).
- **Diff anything against anything.** Your working tree exactly as it sits — staged, unstaged, or committed — any git ref, a live database, a `pg_dump`, or a saved snapshot, on either side of the diff ([sources](#sources)).
- **Editor, local database, and remote stay in sync.** The scaffolded config carries a JSON `$schema` (VS Code autocompletes and validates every key), `--watch` re-diffs on each save, named `environments` point any command at local/staging/production, `migrations` reconciles disk files against each target's applied history, and `--fail-on-diff` turns any pair into a CI drift gate.
- **Agent-enforced discipline.** The package ships a governance bundle for Claude Code and Codex — an operating rule, a workflow skill, and wired PreToolUse hooks that block hand-edits to generated migrations ([built for AI agents](#built-for-ai-agents)).
- **Proof, not review-vibes.** `check` statically gates replay safety and lock hazards on any migration (yours or another tool's), `verify` applies twice in disposable databases and requires the re-diff to converge to zero, and `corpus`/`selfcheck` are the engine's own correctness oracles.

### Accuracy: the diff says what you meant

The harness scores diff **content** against a ground-truth change manifest — recall, precision, F1 — where whole-table rewrites to change one column and destructive drop+create of data-bearing objects count against precision. pg-diverge measures **F1 1.000** in both modes at every scale. Every Supabase engine measures **0.982 at 50 tables and 0.999 at 1,000/2,500 — each one silently dropped the RLS policy-predicate change** (the same miss, diluted by larger manifests).

This is the metric that matters most: a slow diff costs you seconds, an unreplayable diff costs you a deploy, but a diff that silently omits a policy change ships a tenant-isolation hole that review, CI, and the migration runner will all wave through.

### Replay safety: applies once, applies twice, lands on target

![XL fixture correctness](docs/benchmarks/xl-correctness.svg)

Three checks per engine: the migration **applies once**, **applies a second time** (what a crashed deploy or replayed environment needs), and the resulting **catalog matches the target**. Every engine passes apply-once and catalog parity. The split is the second apply: Supabase engines emit unguarded `ADD COLUMN`/`CREATE INDEX`, so their migrations fail re-runs on every fixture containing column or index changes; pg-diverge passes everywhere because every statement is guard-rendered. Per-fixture charts: [additive](docs/benchmarks/additive-correctness.svg) · [functions-policies](docs/benchmarks/functions-policies-correctness.svg) · [realistic](docs/benchmarks/realistic-correctness.svg) · [xxl](docs/benchmarks/xxl-correctness.svg).

## How It Works

1. **Extract** — every statement is classified through the real PostgreSQL parser (`libpg-query`), never regex; live databases are read with batched read-only `pg_catalog` queries.
2. **Compare** — objects match by stable identity and a location-stripped parse-tree hash, so the same definition in a SQL file and a live catalog hashes identically across keyword case, type aliases, constraint placement, and guard spellings. Privileges are modeled as deltas, so real-catalog ACL noise never reads as drift.
3. **Plan** — operations order topologically along AST-collected dependency edges; column changes become per-column `ALTER`s; everything destructive is hint-gated.
4. **Render** — guarded, normalized SQL with a lock/statement-timeout preamble and an embedded lineage marker; `CREATE INDEX CONCURRENTLY` splits into a `.concurrent.sql` companion under the `postgres` adapter.
5. **Gate** — writes are no-clobber, and the lineage chain gate refuses a migration whose from-state doesn't continue the newest pending one.
6. **Verify** — the migration applies **twice** in disposable databases, one transaction per file (mirroring `supabase db push`); the catalog fingerprint must equal the target's, and a reconvergence re-diff must report **zero** residual operations.

## Install and Use

```bash
npm install --save-dev pg-diverge
```

Install scaffolds `pg-diverge.config.json` with its `$schema` pointer. In a Supabase project the database URL auto-discovers from `supabase/config.toml`; otherwise use `--database-url`, `PG_DIVERGE_DATABASE_URL`, or named `environments` with `--env`. Requirements: Node `>=22`, PostgreSQL `15+`, schema-qualified SQL. `npx pg-diverge doctor` diagnoses a misbehaving setup in one report.

```bash
npx pg-diverge diff      # 1. edit supabase/schemas/**, render the migration
npx pg-diverge check     # 2. gate replay safety and lock hazards
npx pg-diverge verify    #    prove it end to end in disposable databases
supabase db push         # 3. apply through your runner — pg-diverge never touches your real databases
```

CI needs two gates (recipes, the composite GitHub action, and a husky snippet in [docs/ci.md](docs/ci.md)):

```bash
npx pg-diverge diff --fail-on-diff --quiet        # exit 3 if database and tree diverged
npx pg-diverge verify --from "git:origin/$BASE_REF"  # the PR's migration applies twice, lands on target
```

## Commands

Zero-flag defaults everywhere: `--from` resolves to the database (then `git:HEAD`), `--to` to the config schema tree, migrations land in `config.migrationsDir` with a derived name, `check` gates the whole migrations directory, `verify` proves the newest pending migration. Applied defaults print to stderr.

| Command | Does |
| --- | --- |
| `diff` | Render the replay-safe migration into the migrations directory (`--fail-on-diff` CI gate, `--watch` editor loop, `--out stdout`, `--write-hints`, `--timing`) |
| `check` | Static replay-safety/lock-hazard gate for the migrations directory or named files, even other tools' (`--reporter github\|sarif\|json`, stdin via `-`) |
| `verify` | Apply-twice + catalog-parity + reconvergence proof for the newest pending migration (`--keep-databases` for debugging) |
| `plan` / `inspect` / `fingerprint` | JSON diff plan · extracted model · one-line schema-equality hash |
| `migrations` | Disk files vs a target's applied history: applied / pending / ghosts / out-of-order |
| `sync` | Gate pending migrations, then (opt-in `--local`/`--remote`) drive the Supabase CLI |
| `audit` | Support-matrix coverage for adopting an existing schema |
| `corpus` / `selfcheck` | The engine's own correctness oracles ([docs/corpus.md](docs/corpus.md)) |
| `doctor` / `init` / `completion` / `explain` | Environment triage · config scaffold · shell completions · offline diagnostic decoder |

Full flags: [docs/commands.md](docs/commands.md). Exit codes: `0` ok · `1` runtime error · `2` diagnostic errors · `3` drift found.

## Sources

Any source can be either side of a diff — and diff generation never creates a database, runs Docker, or uses a shadow database. `dir:` reads files exactly as they sit on disk, so edits diff immediately whether staged, unstaged, or committed; `git:` pins either side to any ref.

| Source | Reads |
| --- | --- |
| `dir:supabase/schemas` | the declarative SQL tree in your working tree, staged or not |
| `git:HEAD` (any ref) | the tree at a git ref, scoped to `schemaPaths` |
| `database:$DATABASE_URL` | a live catalog via read-only `pg_catalog` queries |
| `dump:path.sql` / `dump:-` | one SQL file, or stdin (`pg_dump --schema-only \| pg-diverge diff --from dump:- ...`) |
| `catalog:path.json` | a saved `inspect` snapshot for air-gapped or point-in-time comparisons |

## Safety Model

- Destructive changes are **hint-gated**: drops, replaces, column drops, and type changes need the exact object key in `hints.destructive`; column changes then render as data-preserving `ALTER`s, never table rewrites.
- Renames are **never inferred** — `hints.renames` only. `CASCADE` is **never emitted**. Idempotency is **required**, not optional.
- Incompatible view/routine replacements are blocked until hinted; data statements (`INSERT`/`UPDATE`/`DELETE`/`DO`) are never modeled as schema changes; unsupported DDL emits a blocking diagnostic instead of passing through.
- `transactionMode: "per-migration"` makes `verify` execute exactly the way transactional runners apply files.
- Diagnostics redact credential shapes (URL passwords, JWTs, secrets). Recovery for blocked plans: [docs/hints.md](docs/hints.md) · config reference: [docs/config.md](docs/config.md).

## Built for AI Agents

The npm package ships a ready-made governance bundle so coding agents follow the tree→diff→verify lane instead of hand-authoring SQL:

- `AGENTS.md` — the operator brief: invariants, zero-flag commands, recovery codes.
- `.claude/rules/pg-diverge.md` + `.codex/rules/pg-diverge.rules` — the migration policy rule for Claude Code and Codex: schema intent changes only in the tree, generated artifacts are never hand-edited, destructive hints require human review, lineage gates are honored.
- `.claude/skills/pg-diverge/` (mirrored at `.agents/skills/`) — the step-by-step workflow skill, including the diagnostic-recovery table for every blocking `PD_*` code.
- `.claude/hooks/` + `.claude/settings.json` and `.codex/hooks/` + `.codex/hooks.json` — wired PreToolUse hooks for both runtimes that **block any edit to a file carrying the `-- pg-diverge: lineage` marker**, in Claude Code and Codex alike.

Copy the surfaces into a repo (or point agents at `node_modules/pg-diverge/`) and the discipline is enforced at write time, not just documented. `pg-diverge explain <PD_CODE>` keeps every diagnostic decodable offline, and `--reporter github|sarif|json` keeps `check` output machine-readable.

## Library API

Everything the CLI does is callable directly:

```ts
import {
  extractSourceModel, // any source prefix -> SchemaModel
  extractCatalogModel, // live pg_catalog -> SchemaModel
  planSchemaDiff, // two models -> MigrationPlan
  renderMigrationSplit, // plan -> { sql, concurrentSql? }
  checkMigrationSql, // SQL -> replay-safety/hazard diagnostics
  verifyMigration, // apply-twice + reconvergence proof
  migrationsStatus, // disk files vs applied history
  syncMigrations, // gate + orchestrate the migration runner
  runCorpus, // the corpus oracle
  resolveDatabaseUrl, // flag/$ENV > PG_DIVERGE_DATABASE_URL > supabase/config.toml
  parseLineage, // read the lineage marker from migration SQL
  loadConfig,
} from "pg-diverge";
```

Contracts include `Diagnostic`, `SchemaModel`, `MigrationPlan`, `MigrationsStatusReport`, `SyncResult`, `CorpusReport`, and `PgDivergeConfig`.

## Scope and Stability

The first release models schemas, extensions, types/enums/domains, tables, constraints, indexes, sequences, functions/procedures, views/materialized views, triggers, RLS, policies, grants/default privileges, foreign data wrappers/servers/foreign tables, and comments. Deliberate non-goals (partitioning, publications/subscriptions, event triggers, collations) fail closed with diagnostics ([docs/support-matrix.md](docs/support-matrix.md)). Pre-1.0: pin an exact version in CI; behavior changes surface as named diagnostic codes. Worked Supabase and generic PostgreSQL setups live under `examples/`.
