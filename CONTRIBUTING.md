# Contributing to supaschema

Thanks for your interest in contributing. supaschema is a Node 22.12+ TypeScript CLI and library that generates deterministic, replay-safe PostgreSQL/Supabase migrations from declarative SQL tree diffs. This guide covers local setup, the engineering contract, how migrations and tests work, and the pull-request checklist.

By participating you agree to our [Code of Conduct](./CODE_OF_CONDUCT.md).

## Development setup

Requirements:

- **Node 22.12 or newer** for package compatibility. Local development uses the exact runtime in `.nvmrc`; run `nvm use` or `fnm use`.
- **npm** — this is an npm-only project. Do not introduce pnpm, yarn, or an alternate lockfile, and keep `package-lock.json` intact.

Install and verify a clean checkout:

```bash
npm ci                # clean, lockfile-exact dependency install
npx lefthook install  # explicit maintainer hook installation
npm run check         # build + lint + typecheck + tests
```

Package installation has no lifecycle hook. Maintainers install the [lefthook](https://lefthook.dev) git hooks explicitly with `npx lefthook install`. After that:

- **pre-commit** formats staged files across every language owner in parallel and re-stages the fixes: Biome (JS/TS/JSON/CSS), Prettier (MD/MDX/YAML), taplo (TOML), and sh-syntax (shell). Lanes with no staged files are skipped.
- **pre-push** runs `npm run typecheck` and `npm run guard` (the repo guard suite).

Do not bypass hooks with `--no-verify` or `LEFTHOOK=0`. Fix the failure locally; CI runs the same gates.

| Command | What it does |

Run the **narrowest** command that proves your change, then broaden when you touch shared planner, parser, renderer, hook, or package surfaces.

## Engineering contract

These rules are non-negotiable; they keep the generator deterministic and the package publishable. The full operating brief lives in [`AGENTS.md`](./AGENTS.md).

- **npm only.** No pnpm/yarn, no alternate lockfile. Preserve `package-lock.json`.
- **ESM only.** The package is `"type": "module"` with NodeNext resolution. Use explicit `.js` import extensions in TypeScript (`import x from "./y.js"`). Do not introduce CommonJS (`require`, `module.exports`, `__dirname`).
- **AST over regex for SQL.** Classify, compare, and mutate DDL through PostgreSQL parse trees (`libpg-query`) and the structured model helpers — never ad hoc regex. Regex is fine only for outer transport concerns (patch headers, file markers, secret redaction), not SQL semantics.
- **Fail closed.** Unsupported or ambiguous DDL must fail with an actionable `SUPA_*` diagnostic, never silently pass through.
- **Source lives in `src/**`.** `dist/\*\_`is generated by`npm run build`; never hand-edit it. CLI behavior is owned by `src/cli.ts`and`src/cli/\*\*`; library exports by `src/index.ts`; config semantics by `src/config/schema.ts`plus the generated`supaschema-config.schema.json` (keep them, the docs, and examples aligned).
- **Diagnostics redact secrets** (URL passwords, JWTs, tokens) and must be actionable.
- **Provide both surfaces.** When a capability is reusable, expose it as both a CLI command/flag and a typed library API.

## How migrations work

supaschema does not author migration SQL by hand and neither should you.

- **Schema intent** lives in the declarative SQL tree configured by `schemaPaths` in `supaschema.config.json` (for consumers: `supabase/schemas/**`, `database/schemas/**`, etc.). Migrations are **rendered** from that tree with `supaschema diff`.
- Any `.sql` file containing the `-- supaschema: lineage` marker is a **generated artifact**. Never edit it by hand — change the source tree and regenerate. (A repo PreToolUse hook blocks direct edits to these files.)
- Migrations are **idempotent and replay-safe** by construction: guarded creates (`IF NOT EXISTS`, catalog-checked `DO` blocks), no `CASCADE`, lock-safety preserved. Any change you make must keep these guarantees.
- **Destructive operations** (drops, table/type replacements, column drops or type changes, incompatible view/routine replacements) stay blocked until the exact object key is added to `hints.destructive` after reviewing the rendered SQL. `"*"` never lands in committed config.
- **Renames** are declared in `hints.renames`, never inferred.
- Decode any `SUPA_*` code with `supaschema explain <CODE>`; recovery procedures are at the [hints reference](https://supaschema.com/docs/configuration/hints).
- `transactionMode: "per-migration"` is the default for transactional runners (e.g. `supabase db push`); `CREATE INDEX CONCURRENTLY` is blocked there and belongs only in an explicit `per-statement` operational lane.

When changing the planner or renderer, run `supaschema check` (replay-safety gate) and, when a database is reachable, `supaschema verify` (apply-twice proof).

## How tests work

- Tests live in `tests/**` and run with **Vitest** (`npm test`).
- Fixtures under `tests/fixtures/**` and `corpus/**` are **behavioral evidence**. Update a snapshot only when the rendered SQL change is **intentional** and explained by your source change — call it out in the PR.
- The two determinism oracles are first-class:
  - `npm run fixture:verify` renders a fixture migration, applies it twice, and compares the resulting catalogs.
  - `npm run corpus:check` runs the dirty-real corpus reconvergence oracle when a database is reachable.
- `tests/core/property.test.ts` uses `fast-check` for property-based parser, replay, migration-name, and redaction checks. For SQL extraction, planning, rendering, checking, verifying, typegen, or CLI-default changes, run the colocated tests plus `npm run typecheck`. For package/release/agent-surface changes, run `npm run check:package` or `npm pack --dry-run`.

## Changesets and releases

Any user-facing change (behavior, CLI, config, diagnostics, docs that ship) needs a changeset while the change is fresh:

```bash
npm run changeset
```

Pick the semver bump (patch/minor/major) and write a short, user-readable note. Commit the generated `.changeset/*.md` file with your PR.

`main` is the npm release source. Release PRs follow [Release](./docs/release.mdx): run `npm run release:version`, confirm `npm run release:notes -- --version <version>`, and run `npm run release:verify`. The top `CHANGELOG.md` entry is the canonical GitHub Release body.

## Pull-request checklist

Use the [PR template](./.github/PULL_REQUEST_TEMPLATE.md) as the current checklist.

Every update to `main` uses a protected pull request. Before merging, run:

```bash
npm run github:audit-settings
```

Merge PRs with GitHub's squash path:

```bash
gh pr merge <number> --squash --delete-branch
```

Release changes also follow [Release](./docs/release.mdx).

## Reporting bugs and requesting features

Use the [issue templates](./.github/ISSUE_TEMPLATE). Never paste real connection strings, passwords, JWTs, or tokens. For security vulnerabilities, follow [`SECURITY.md`](./SECURITY.md) — do not open a public issue.
