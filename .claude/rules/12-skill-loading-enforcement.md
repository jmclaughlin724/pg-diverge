# Rule 12 — Deterministic hook context and skill-loading enforcement

## Contract

This rule owns deterministic hook context and skill-loading enforcement: hook state selects relevant skills, skill loads are observable-only, and governed work is blocked until required context is loaded.

Relevant project skills are selected and enforced by hook state, not by model judgment. Claude Code documents hooks as lifecycle commands that receive JSON on stdin and can add model-facing context with `hookSpecificOutput.additionalContext`; use that field for steering and reserve `systemMessage` for user-facing UI warnings (https://code.claude.com/docs/en/hooks). Claude Code skills expose `description` and `when_to_use` to help the model decide when to invoke a skill, but deterministic load-before-write behavior belongs in `PreToolUse` enforcement, not in skill prose (https://code.claude.com/docs/en/skills).

## Runtime map

- `SessionStart` injects standing context and handles context lifetime deliberately. `startup` and `clear` reset state, while `resume` and `compact` invalidate context-loaded skill evidence without carrying it into the next prompt. Claude and Codex both document `startup`, `resume`, `clear`, and `compact` as session-start matcher values; `compact` is the post-compaction re-injection point (https://code.claude.com/docs/en/hooks, https://developers.openai.com/codex/hooks).
- `UserPromptSubmit` scores prompt text with explicit `$skill` and `/skill` tokens, non-generic skill names, and curated `metadata.keywords`. It does not score `description`, `when_to_use`, command prose, or legacy pattern metadata. Explicit `$skill` and `/skill` tokens MUST all remain pending until loaded; keyword-only matches MAY be capped to control noise. Repo-managed skill frontmatter must not add `intent-patterns:`; use literal `metadata.keywords` and `metadata.file-triggers` instead. Matches are recorded as pending with their `SKILL.md` paths and injected as model-facing context with an imperative observable-load command.
- `PreToolUse` allows the agent's next tool call to acquire required context while a skill is pending: observable skill-loading calls and Code Atlas query calls are allowed. It hard-blocks governed command, content, delegation, and research tools only when the attempted tool call is neither an observable skill load nor a Code Atlas query. Tool-scope matching uses structured file paths from payloads and patch headers against `metadata.file-triggers`; it does not scan command text for prompt keywords. Codex shell command tools are governed, but only structured reader command segments that target `SKILL.md` count as observable loads; non-reader command segments that merely print, echo, or mention `SKILL.md` MUST NOT clear pending skills. Reader detection MUST use the shared shell command parser and MUST recognize nested `bash -lc` / `sh -c` / `zsh -c` reader commands, multiple `SKILL.md` paths in one command, POSIX separators, Windows separators, and simple skill-name brace alternates. The denial uses `hookSpecificOutput.permissionDecision = "deny"` on tool events, matching the Claude and Codex hook contracts (https://code.claude.com/docs/en/hooks, https://developers.openai.com/codex/hooks). Denial feedback MUST tell the agent the exact observable skill-load command to run and MUST avoid passive "may load" phrasing. Advisory context is emitted only for newly pending file-triggered skills and at most one Code Atlas `pre-edit` hint per target per turn; already loaded skills and repeated no-op matches stay silent.
- Inside a subagent the `PreToolUse` skill gate is advisory, not blocking. Claude Code fires `PreToolUse` for tool calls made inside a subagent and marks them with an `agent_id` field present only for in-subagent calls (https://code.claude.com/docs/en/hooks), but `SubagentStart` cannot block and a subagent may run under a restricted `tools:` set without `Skill`/`Read`, so a hard deny would deadlock it with no way to clear the gate. When `agent_id` is present the gate emits the pending-skill names as `additionalContext` instead of denying; hard enforcement stays in the main session and the orchestrator applies subagent findings. The response-evidence gate downgrades the same way, because a subagent cannot revise the parent's final response.
- `PostToolUse` records observable skill loads and structured evidence breadcrumbs, including successful `code_atlas_query`, `npm run code-atlas:query`, and `node scripts/code-atlas/query.mjs` calls. Command evidence MUST be limited to recognized verification domains such as guard, test, typecheck, lint, package, build, sync, GitHub checks, and Code Atlas. Source and inventory reads such as `sed`, `cat`, file reads, and ad hoc inspection commands MUST NOT become verification evidence or failed verification blockers based on stdout, stderr, or transcript text. Command outcome parsing MUST trust structured status and exit fields or execution-status lines such as `Process exited with code 0`; it MUST NOT scan arbitrary source output such as `process.exitCode = 2` for exit codes. A skill clears only when the `Skill` tool loads it or an actual `SKILL.md` file read is observed through `Read`, MCP, or a shell reader command exposed by Codex; shell-read detection MUST normalize POSIX and Windows path separators before matching `*/skills/*/SKILL.md`. Slash commands, `$skill` tokens, inline mentions, and Code Atlas queries are request/evidence signals, not skill loads.
- `SubagentStart` injects pending skill context because non-fork subagents start with fresh isolated context and do not inherit loaded skills or files already read by the parent (https://code.claude.com/docs/en/sub-agents). Use subagent frontmatter `skills:` when a subagent must preload full `SKILL.md` content (https://code.claude.com/docs/en/sub-agents).
- In the shared context hook layer, `Stop` and `SubagentStop` run response-shape detectors and return `decision: "block"` when corrections are required. Claude documents Stop/SubagentStop `decision: "block"` as the control that prevents stopping and feeds the reason back to Claude; Codex Stop/SubagentStop use the same JSON stdout shape through the shared payload adapter (https://code.claude.com/docs/en/hooks, https://developers.openai.com/codex/hooks).
- `TaskCompleted` and `PermissionDenied` are Claude-only enforcement points in this repo. Codex does not currently document those events in its hook matcher table, so `.codex/hooks.json` intentionally omits them (https://developers.openai.com/codex/hooks).
- `SessionEnd` clears session state. Claude documents SessionEnd as cleanup-only with no decision control (https://code.claude.com/docs/en/hooks).

## State and ownership

- State lives under `.tmp/agent-hooks` by default and is keyed by a path-safe validated session id. Enforcement facts that can become stale across prompts — pending skills, response corrections, evidence breadcrumbs, one-shot Code Atlas advisories, and the last prompt — are scoped to the active turn (`turn_id` in Codex, prompt sequence in Claude). Context-loaded skill evidence is scoped to a context epoch and is invalidated on resume/compact. Hook handlers MUST serialize session-state mutation through `scripts/agent-hooks/state.mjs` so parallel `PostToolUse` events cannot overwrite observed skill loads or evidence from the same session.
- Canonical hook source lives in `.claude/hooks/**` and shared logic lives in `scripts/agent-hooks/**`. `npm run sync:llm` mirrors `.claude/hooks/**` into `.codex/hooks/**`; edit the Claude owner and sync instead of hand-editing generated mirrors.
- Skill authoring standards and templates must route deterministic skill loading through this hook path. New SKILL.md metadata fields are inert until `scripts/agent-hooks/skills.mjs` reads them and `scripts/guards/agent-surface/check-agent-hooks.mjs` validates them; do not document a custom field as active enforcement before both owners exist.
- `scripts/skills/sync-llm.mjs` is the only writer for generated agent-surface mirrors and generated source-repo Codex hook registration. Preserve its atomic write path: generated files are written through unpredictable temp names, exclusive creation, and rename, with symlink/race regression coverage in `tests/agent-surfaces.test.ts`.
- `.claude/settings.json` is the maintainer Claude context-hook registration owner. Source-repo Claude Bash `PreToolUse` MUST resolve through `.claude/hooks/context-pre-tool-use.mjs`; do not also register `.claude/hooks/guards/bash-policy-checks.mjs` as a direct source Claude `PreToolUse` hook. `scripts/skills/sync-llm.mjs` MUST validate that Claude registration before rendering `.codex/hooks.json`. Generated `.codex/hooks.json` MUST register repo-local Codex context enforcement hooks for `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop`, and `Stop`. Source-repo Codex shell command tools MUST match exactly one `PreToolUse` hook command: `.codex/hooks/context-pre-tool-use.mjs`. `scripts/agent-hooks/runner.mjs` MUST dispatch skill/evidence gating and Bash safety through `.claude/hooks/guards/bash-policy-checks.mjs` from that single source-repo context path. Shared Codex context hook scripts remain generated mirrors of Claude hook sources. Consumer Codex hook templates under `agent-bundle/codex/hooks.*.json` MUST strip repo-local context enforcement hooks and MUST keep `.codex/hooks/general-guard.mjs` as the standalone consumer Bash safety boundary.
- Rule 22 owns generated agent-surface sync and Codex hook registration. Required source-repo hook runtime, Claude rules, generated Codex rule mirrors, and `.claude/settings.json` are tracked branch surfaces when tracked hook registration or guards depend on them. Keep optimizer skills, maintainer-only agents, personal overlays, Code Atlas internals, MCP/deployment configs, private services, and generated state gitignored. Rule 13 keeps source-only context hooks and `scripts/agent-hooks/**` out of npm package and consumer scaffold output unless the consumer contract explicitly changes.
- `scripts/guards/agent-surface/check-hook-import-graph.mjs` proves hook runtime modules import only `node:` builtins and relative files, so hooks run without package installation.

## Response-shape policy

Stop-time detectors enqueue and auto-resolve session-scoped corrections for hedge density, completion claims with open items, verification claims without evidence breadcrumbs, mechanism-only correctness answers without architecture/end-state and verification disposition, decision menus after direct directives, deferral language, and tool failure without retry. Mechanism means what the runtime, hook, tool, or upstream implementation actually does. Architecture/end-state means the canonical owner, single entry point, `$elegant` target shape, and whether the current topology matches it. Verification means source or command evidence plus failures, skipped checks, and blockers. Diagnostic, review, verification, source, why, correctness, best-practice, redundancy, and architecture-shaped turns MUST NOT end with only runtime mechanism or upstream-valid behavior. They MUST name the local `$elegant` end-state disposition and the verification disposition before claiming correctness. `mechanism-claim-without-architecture` MUST block mechanism-only correctness answers through Stop/SubagentStop response-shape enforcement. GitHub, PR, CI, branch-green, or check-green claims MUST have recorded successful `github-checks` evidence. A failed `gh pr view --json statusCheckRollup`, `gh pr checks`, `gh run view`, or GitHub Actions API evidence item MUST stay unresolved until a later successful evidence item for the same command or `github-checks` domain exists. A response MUST NOT claim GitHub checks are green while live `statusCheckRollup` failure evidence remains unresolved. In the main session `PreToolUse` also blocks further edits while evidence-related corrections remain unresolved; inside a subagent (`agent_id` present) that block is downgraded to advisory `additionalContext` so the subagent is not deadlocked, and `SubagentStop` corrections must not strand the parent's edit gate.

STOP if a governed surface is edited while a matched required skill is pending, if a `PreToolUse` gate hard-denies a subagent tool call (`agent_id` present) instead of downgrading to advisory, if hook output uses `systemMessage` where model-facing context is required, if a hook failure silently allows a governed action, if generated mirrors drift from their `.claude/**` owner, if a tracked hook registration or guard depends on a gitignored source-repo runtime file, if GitHub checks are claimed green without successful `github-checks` evidence or while failed `statusCheckRollup` evidence remains unresolved, if a source or inventory read is recorded as verification evidence or a failed verification blocker, if source-repo Claude or Codex shell commands match more than one `PreToolUse` Bash safety hook command, if hook event handlers bypass serialized session-state mutation, or if `sync-llm` reintroduces predictable temp paths, check-then-write mirror writes, or symlink-following temp-file behavior.

## Verification

When hook state, skill matcher, context injection, response-shape detectors, generated mirrors, or runtime adapters change, run:

```bash
npm run sync:llm
npm run guard:agent
npm run guard
```

Run focused hook/skill-matcher tests for the changed module. For GitHub check evidence behavior, run:

```bash
npm test -- tests/agent-hook-core.test.ts
```

For session-state concurrency behavior, `tests/agent-hook-core.test.ts` MUST cover parallel Codex `PostToolUse` skill loads for the same session. For Codex shell-read skill loads, `tests/agent-hook-core.test.ts` MUST cover POSIX separators, Windows path separators, one nested shell reader command that loads multiple pending skills, non-reader `SKILL.md` command tokens that must not clear pending skills, and preservation of every explicit skill token beyond keyword-match caps.

## Failure behavior

Fix the canonical `.claude/**` hook, `.claude/settings.json` registration, or shared `scripts/agent-hooks/**` owner, then sync generated mirrors and `.codex/hooks.json`. Do not patch generated mirrors directly, use user-facing `systemMessage` for model steering, or fail open on governed writes.

## Done means

Required skills are detected and loaded before governed work, context epochs reset correctly, mirrors are synced, hook graph imports are safe, GitHub check claims are backed by successful `github-checks` evidence, unresolved failed evidence blocks green claims, and response-shape gates still operate.
