# supaschema Migration Policy

## Contract

This rule owns how schema migrations are produced and protected in a repo that uses supaschema: migrations are generated from the declarative end-state plus migration-derived source intent, generated artifacts are never hand-edited, destructive intent is hint-gated, and verification mirrors the migration runner. Existing migrations are source intent for the planner, not only history files. The bundled `supaschema` skill explains CLI behavior and diagnostics; this rule remains the workflow and policy owner. Write-time enforcement is hook-owned.

For source-kind and introspection boundaries, use the packaged offline reference at `node_modules/supaschema/agent-bundle/docs/concepts/sources.mdx`. The owner briefs in `src/AGENTS.md`, `src/source/AGENTS.md`, and `src/typegen/AGENTS.md` exist only in the supaschema implementation repository and apply when developing supaschema itself, not in a consuming project.

## Rules

- Consumer migration policy must rely on project files, generated hook context, and supaschema command output. Maintainer tooling such as cclsp, FastMCP, and context-enforcement hooks is tracked in the repo but is not part of the published consumer install surface.
- Consumer setup is package install plus one explicit setup command with the consuming project's package manager. Default `supaschema init` writes config, configured schema directories, configured migration directories, safe generated package scripts when `package.json` exists, package-owned active AI enforcement under `.agents`, `.claude`, and `.codex`, and pending path-confirmation state. Those scripts are focused non-apply lanes: `supaschema:diff` for `supaschema diff`, `supaschema:stage` for `supaschema stage`, `supaschema:types` for `supaschema types`, and `supaschema:check` for the full-directory `supaschema check`; do not scaffold `--changed` as the default check lane or add `db:migration:generate` and other parallel migration-generation aliases. Setup diagnostics, full sync, apply, and database execution verification stay on direct CLI commands (`supaschema config validate`, `supaschema sync`, `supaschema apply`, and `supaschema verify`). It copies missing bundled prompt/rule/skill/hook files, merges package-manager-specific Claude and Codex hook registration, preserves existing non-identical files, and reports skipped non-mergeable hook config for agent repair. It does not write `AGENTS.md`, `CLAUDE.md`, backup directories, maintainer tooling, or apply-capable package scripts. Maintainer-only Claude/Codex optimization and context-enforcement tooling remains repo-local under Rule 13. `supaschema init` is idempotent: existing JSON config files and existing `supaschema:*` package scripts are left untouched unless explicit repair is requested, and JavaScript config files are not loaded or converted.
- Normal resolved installs do not create `.supaschema/`. Supabase projects with an existing `_bootstrap` schema inventory or a `supabase/AGENTS.md` owner brief marking `supabase/schemas/**` as non-generator inventory are resolved installs when the standard Supabase paths are detected: `supaschema init` writes `supaschema.config.json` with explicit `schemaPaths` and `migrationsDir`, then sets `workflow.schema_diff` and `workflow.migration_sync` to manual. If `.supaschema/install.json` records `"pathConfirmationNeeded": true`, inspect the detected candidates, ask the user which `schemaPaths` and `migrationsDir` to use, and update `supaschema.config.json` before the first diff. Do not generate from the installer's guessed first candidate; `config validate`, `doctor`, and zero-source `diff` block until both fields are explicit, and the PostToolUse hook must skip auto-diff until both fields are explicit.
- `supaschema.config.json` owns four workflow decisions. `schemaPaths` owns the recursive declarative tree and default after-state, while `migrationsDir` owns generated output, migration source intent, and lineage proof. `sources.from` owns the before-state; zero-source commands target `dir:<schemaPaths[0]>`, and explicit alternate targets use `--to`. A `migrations:` generation before-state must resolve to the configured `migrationsDir` and replay fail-closed; migration replay is never a generation target. For generation, `sources.from: "auto"` first resolves a proven `git:INDEX` closure. It then selects `migrations:<migrationsDir>` when generated lineage is absent, a hand-authored tail follows the newest lineage edge, or no Git baseline exists; only a contiguous lineage may fall through to `git:HEAD`, and `empty:` is reserved for a first migration with no corpus. Replay errors block generation with `SUPA_MIGRATION_BASELINE_REPLAY_REQUIRED`. Generated contract fields are `typesFile`, `zodFile`, `zodTypesImportPath`, `workflow.type_generation`, `workflow.zod_generation`, and `workflow.type_usage`; `supaschema types` emits the upstream Supabase `Database`, `Tables`, `TablesInsert`, `TablesUpdate`, `Enums`, `CompositeTypes`, and `Constants` contract plus a separate schema-keyed `SupaschemaZod` runtime extension. `SupaschemaZod` carries only CHECK refinements that are loose-or-exact for the client wire path: scalar integer and float8 bounds, non-strict typmod-free numeric bounds, `BETWEEN`, safe integer-literal equality on integer-family columns, typmod-free text/varchar/citext `char_length`, uncollated typmod-free text/varchar `IN`, bare booleans, and null-aware numeric column comparisons. Precision-sensitive pairs require wire-exact small-integer or float8 targets. Casts unwrap only for scalar typmod-free sources and same-base typmod-free text/varchar/citext targets. Scalar columns inherit atomic column fragments from every unambiguously resolved `CREATE DOMAIN` CHECK in their chain through `VALUE`. Real/float4, typmod-constrained numeric, char/bpchar, domain arrays, ambiguous domain hops, explicitly collated list checks, widening or typmod-bearing casts, precision-sensitive arbitrary-numeric or bigint comparisons, and all other uncertain expressions are skipped, never approximated; `NOT VALID` table checks refine `Insert`/`Update` but not `Row`. Direct schema-qualified aliases and `App*Schema` exports are forbidden. RPC generation must preserve postgres-meta's complete signature objects and visibility boundaries: sort arguments by name, retain named variadic inputs, accept unnamed inputs only for exact JSON/JSONB/text or one eligible non-array relation row, exclude domains and arrays from computed relationships, inline physical relation columns in returns, keep computed SETOF fields singular, and emit multi-OUT results as `Record<string, unknown>`. A generated `unknown` is a coverage defect only when modeled relation, function, extension, or expression facts should resolve; unsupported PostgreSQL scalars intentionally retain the upstream `unknown` fallback and must not gain Supaschema-only mappings. Schema-diff hook fields are `workflow.schema_diff`, `workflow.migration_check`, and `workflow.migration_verify`. Apply policy fields are `workflow.migration_sync` and `sync.targets`; one automatic target may run, multiple targets are refused, and remote targets require approval variables.
- Schema end-state changes belong in the configured declarative SQL tree (`schemaPaths` in `supaschema.config.json`), such as `database/schemas/**`, `supabase/schemas/**`, `neon/schemas/**`, `aws-postgresql/schemas/**`, `cloud-sql/schemas/**`, `alloydb/schemas/**`, or `azure-postgresql/schemas/**`. Existing migrations in `migrationsDir` are the operational source-intent corpus for facts the end-state tree cannot express by shape alone and the generated-lineage proof for the migration-tree baseline: row backfills, explicit DML/`DO` workflows, enum rewrite recipes, Vault references or placeholder names, workload-proven index intent, reviewed routine drops, and provider bootstrap constraints. Planning must inspect and structurally model that context before reporting missing intent or trusting a `git:` baseline. Render the migration with `supaschema diff`; do not hand-author migration SQL for changes the tree and migration-corpus lane can express.
- Migration-derived intent is explicit, not guessed. supaschema may preserve or transform row backfills, Vault secret references, and query-workload indexes only when the intent is present in declarative SQL, existing migrations, config, checked workload artifacts, or reviewed hints. It must never invent row values, Vault secret material, tenant predicates, data conversion expressions, or indexes from table shape alone. When a table change drops columns and adds columns in the same transition, destructive hints alone are not data intent; the planner blocks with `SUPA_PLAN_DATA_TRANSITION_REQUIRED` unless the migration corpus contains reviewed DML or `DO` transition intent. When intent is absent, the planner or diagnostic must name the missing source and tell the agent where to add it.
- The implementation lane for diff/plan/sync is: resolve configured `schemaPaths`, `sources`, and `migrationsDir`; extract parser-backed `from` and `to` schema models; extract one structured migration context from existing migrations for source intent plus generated-lineage baseline proof; pass both schema models and migration context into planning/rendering; then check, verify, and reconcile against migration history. Existing migrations cannot be used only for lineage/history while the planner ignores their contents.
- Routine dependencies are part of the parser-backed model. SQL-standard bodies, SQL string bodies, and static PL/pgSQL statements feed relation and column dependencies into planning, checking, and diagnostics. Dynamic SQL, partially parsed PL/pgSQL, and unsupported routine languages fail closed when the same plan changes relations or types unless the routine is rewritten into structurally extractable SQL or the relation/type change moves to a reviewed explicit migration. Column drops and type changes must prove dependent routines, views, policies, and triggers are dropped or rewritten before the table alter; otherwise the planner blocks with a `SUPA_*` diagnostic.
- Do not run raw SQL DDL through Bash or database CLIs for structural changes that belong in the declarative schema tree. Edit the tree, run `supaschema diff`, then run `supaschema check`.
- SQL understanding is AST/model-owned. Classify, compare, or mutate DDL through PostgreSQL parse trees (`libpg-query`) and structured model helpers, not ad hoc regex. Regex is acceptable for outer transport concerns such as hook patch headers, file markers, or redaction, not SQL semantics.
- PostgreSQL support claims are executable contracts, not prose. In the supaschema implementation repository, any object or statement described as supported in docs, skills, or agents must be wired through the model boundary in `src/sql/support.ts` plus the applicable extractor, catalog extractor, planner, renderer, checker, audit report, and focused tests, and any documented unsupported boundary must also be listed in `unsupportedStatementSupport` so parser-backed diagnostics name the boundary instead of falling through generic text. In a consuming project, treat the packaged docs and `supaschema explain` output as the support contract.
- Object keys, storage keys, generated headers, and version formats are consumer contracts. Any change to one must ship a compatibility test in the same change that consumes a payload written against the previous shape (precedent: overlay keys, contract keys, snapshot semver). When the old shape stays accepted, the test pins the compatibility lane; when it is retired, the test proves rejection is explicit rather than a silent misread.
- Any `.sql` file containing the `-- supaschema: lineage` marker and the configured `typesFile` / `zodFile` outputs are generated artifacts. Never edit them by hand. The `generated-artifact-edit` PreToolUse hook blocks direct writes, patch updates, contract deletions, move/delete-add rewrites, literal or assigned shell redirection targets, redirection-aware `cp`/`mv` targets, target-directory forms, `>|`, and bounded write flags such as `--write=<path>`. Only an `apply_patch` delete-only generated-migration change is the reviewed stale-migration recovery lane; Bash deletion and generated-contract deletion stay blocked. The guard fails closed with `SUPA_GENERATED_ARTIFACT_GUARD_FAILED` when malformed hook input or invalid config prevents classification; fix the config or hook input instead of bypassing enforcement. Change declarative SQL or generator config, run `supaschema doctor`, then run `supaschema sync`; use `supaschema types` only when source state already matches. Preserve unexplained drift and review the generated diff. Decode blockers with `supaschema explain SUPA_GENERATED_ARTIFACT_EDIT` or `supaschema explain SUPA_GENERATED_ARTIFACT_GUARD_FAILED`. Use `supaschema diff --replace <migration.sql>` for an unapplied generated migration that must be regenerated from its original lineage baseline. `diff --replace` is the only overwrite lane: the file must be inside `migrationsDir`, contain lineage metadata, match the planned `from` fingerprint, and be absent from any resolvable configured target history table. If the version is already applied, create a forward migration or run an explicit external history-repair workflow instead.
- When the bundled PostToolUse hook is wired and workflow defaults are kept, a write to a schema-tree `.sql` file auto-runs `supaschema diff` then `supaschema check <generated migration path...>`. If `workflow.migration_sync` allows automatic sync, the hook first confirms exactly one `sync.targets` entry is selected with `mode: "auto"`, its database URL reference resolves when its runner needs one, and any remote target has its configured approval variable set; only then does it delegate to `supaschema sync`, which owns the full ordered workflow: enforce apply policy, select at most one target, reconcile migration history before artifact generation, resolve sources, generate the diff, refresh history, check pending migrations, refresh generated TypeScript/Zod contracts according to workflow policy, stage the schema closure when Git is available, run deploy safety gates, verify pending migrations against a disposable database, run the selected target runner when a target is selected, and reconcile or dry-run report. Otherwise the hook stays on the non-mutating diff/check lane and tells agents to run `supaschema sync` when they need the full workflow. If the generated-migration `check` or `sync` fails, the hook emits loop-continuation feedback; inspect the diagnostic, identify the canonical root source in the declarative tree, config, or generated migration chain, search for similar or correlated migration failures, fix the canonical owner, and rerun the failing command. Treat hook context as the authoritative workflow result, resolve any reported `SUPA_*` code before continuing, and do not re-run the diff by hand to "confirm" a clean result. The hook skips multi-root or path-confirmation cases that require human review.
- Never overwrite a migration file outside `supaschema diff --replace`. Normal `diff` writes no-clobber (`SUPA_DIFF_OUTPUT_EXISTS`); named/file-output empty plans are refused with `SUPA_DIFF_EMPTY_PLAN`.
- Honor the lineage chain gate: `SUPA_DIFF_LINEAGE_BROKEN` means resolve a source-backed post-migration baseline such as `git:<ref>`, `dir:<path>`, `dump:<file>`, `catalog:<snapshot>`, or `empty:` after review; `SUPA_DIFF_LINEAGE_DUPLICATE` means the change is already pending. `--no-check-chain` requires explicit human approval.
- The baseline contract is a staged schema closure: a generated migration's lineage `to=` fingerprints the on-disk schema tree at generation time, uncommitted edits included (`SUPA_DIFF_TREE_UNCOMMITTED` warns at generation from a dirty tree). `supaschema sync` stages the schema tree, generated migration, explicitly selected config, and regenerated type/Zod outputs together. With `sources.from: "auto"`, the next edit uses a proven `git:INDEX` snapshot when available, replays the configured migration corpus for adoption or a manual tail, and uses `git:HEAD` only for contiguous lineage. The migration may already be applied or still pending in target history; either state can continue through a new forward migration. Commit one or more complete staged closures before handoff or merge, but a commit is not required between schema edits.
- Diff generation preflights the workspace before planning whenever `dir:` is the target. Generated-contract, config-scope, and out-of-scope-schema dirtiness block on every baseline. Migration-file dirtiness blocks for Git baselines (uncommitted files are invisible to `git:INDEX`/`git:HEAD`), for any dirty migration on a scoped `--schema` diff (a scoped diff cannot prove the tail's scope), and for lineage-bearing (generated) dirty files under a `migrations:` replay baseline; a hand-authored tail is legitimate replay input for an unscoped `migrations:` baseline and must not be blocked. Diagnostics: `SUPA_DIFF_GENERATED_CONTRACT_DIRTY`, `SUPA_DIFF_MIGRATIONS_DIRTY`, `SUPA_DIFF_CONFIG_DIRTY`, and `SUPA_DIFF_SCOPED_DIRTY_SCHEMA`. Do not bypass these diagnostics with hints or alternate baselines; repair the staged closure or close the owning migration unit first.
- `SUPA_MIGRATION_BASELINE_MISMATCH` recovery: compare the pending chain-end lineage `to=` fingerprint against the current `git:INDEX`, `git:HEAD`, and worktree schema fingerprints. If the recorded end-state is reproducible, stage the matching complete closure or regenerate from that state with `supaschema diff --replace`. If the end-state is not reproducible and no configured target records the version as applied, review its SQL, delete the pending migration after any required owner approval, then regenerate from the current tree.
- Destructive operations (drops, table/type replacements, column drops, column type changes, incompatible view/routine replacements) stay blocked until the exact object key is added to `hints.destructive` after reviewing the rendered SQL. `"*"` never lands in committed config. Migration-intent destructive comments are disclosure/audit evidence, not an additional blocker after the planner has allowed the operation. A hinted table replace is not data-preserving; prefer the column ALTER lane the planner renders for identity, default, not-null, generated-expression, additive-column, and constraint-only changes.
- Dropped parent objects own the state PostgreSQL removes with them. Gate the parent drop key and suppress separately rendered child grants, comments, RLS, policies, triggers, constraints, and indexes that are owned by that dropped object. Privilege replacements must revoke the previous privilege state before granting the target state, and removing a modeled `REVOKE` must render the reverse `GRANT`.
- Renames are declared in `hints.renames`, never inferred. Kind changes and cross-schema moves are unsupported by design.
- Run `supaschema check` on every generated or hand-authored migration. Run `supaschema verify` before merge when a database is reachable; keep `transactionMode: "per-migration"` for transactional runners such as `supabase db push`.
- `CREATE INDEX CONCURRENTLY` is blocked when `transactionMode` is `per-migration`; under `per-statement` it lands in the `.concurrent.sql` companion, which runs outside a transaction through an operational lane.
- `supaschema sync` is the canonical one-command workflow. It generates the diff, selects at most one configured target, reconciles migration history, gates replay safety, refreshes generated TypeScript/Zod contracts according to workflow policy, stages the schema closure when Git is available, runs deploy safety gates, verifies the ordered pending migration set against a disposable database, applies through the selected runner when a target is selected, and performs final reconciliation or dry-run reporting. It also refreshes generated contracts and runs the schema-closure staging lane when no migration is pending. `supaschema diff`, `supaschema stage`, `supaschema apply`, `supaschema types`, and `supaschema check` remain explicit lanes for focused operation: `diff` writes migrations, `stage` git-stages changed generated migration files, `apply` applies already-generated pending migrations, `types` regenerates TypeScript/Zod contracts, and `check` gates replay safety. Bare `sync` may select one configured `sync.targets.<name>` entry with `mode: "auto"` when `workflow.migration_sync` is `"auto"`; multiple automatic targets are refused because cross-target apply is not atomic. `workflow.migration_sync: "manual"` leaves bare `sync` on the dry-run gate and allows explicit `--target <name>` overrides. `workflow.migration_sync: "disabled"` refuses apply while allowing non-mutating sync lanes. Remote automatic targets must require a runtime approval variable such as `SUPASCHEMA_REMOTE_SYNC_APPROVED=1`. Until target resolution, safety gates, verify, and runner support have executed successfully, agents must not mutate a database.
- Database URLs resolve flag (`$ENV` indirection supported) > named `config.environments` entry via `--env` > `SUPASCHEMA_DATABASE_URL` > nearest `supabase/config.toml`. Do not hard-code connection strings in scripts, config, or CI, and do not create duplicate supaschema-only credential variables when the project already has a database URL variable or provider runner credential lane.
- Decode any `SUPA_*` diagnostic with `supaschema explain <CODE>` and use the emitted diagnostic guidance as the recovery procedure.

## Verification

For schema workflow changes or consumer migration guidance, prove the actual lane with the relevant command:

```bash
supaschema diff
supaschema check
supaschema verify
supaschema types
supaschema explain <SUPA_CODE>
```

When developing supaschema itself in its implementation repository, run the narrow source tests plus `npm run typecheck` and the relevant fixture/corpus checks. In a consuming project, validate through the consumer lanes above and the project's own package scripts.

## Failure behavior

Resolve `SUPA_*` diagnostics through `supaschema explain`, edit the declarative tree rather than generated migrations, and ask for explicit approval before any remote sync approval, apply flag outside configured automation, or `--no-check-chain` path.

## Done means

Schema end-state is in the tree, migration-derived source intent has been extracted or a missing-intent diagnostic names the required source, generated migration/types/Zod outputs are current, generated artifacts were not hand-edited, destructive/rename intent is explicit or disclosed according to the planner decision, and check/verify evidence exists for the touched lane.
